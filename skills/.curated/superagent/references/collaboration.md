# 目标委派与持续协作

本篇说明目标归属、工作区拓扑、宿主接入、长会话状态恢复、协作面板与外部协作、外部事件监听、前台执行门禁、宿主子代理分工、面向用户的转述方式与交付验收流程。直接发起和管理外部 Codex worker 见 [Codex SDK 编排](sdk-orchestration.md)，接管存量 CLI 会话见[存量 CLI 会话的旁路监控与推进](cli-monitoring.md)。

## <a id="goals-and-workspaces"></a>目标委派与工作区划分

直接转发用户原话。只补执行者缺少的必要背景和实际生效的协作约束，例如目标工作区、已确认的写入和授权范围、跨任务依赖、共享产物归属和交付位置。背景材料可直接附上，也可给出执行者确实可读的路径或链接。把完整目标交给一个具备[对应能力、工具和权限](#host-subagents)的负责人，由其决定实现路线、验证方式和内部子任务拆解。

例如，用户提出“做一个 2D 鹈鹕骑自行车的 HTML”，就把这句话原样传给执行者，只补上允许写入的目录与最终文件路径；动画算法、交互细节和结构组织全部交给执行者自行拍板。目标负责人也可在自身权限内调动原生子代理并行处理子问题。

根据磁盘写入冲突面和集成关系安排工作区拓扑：

| 任务关系 | 协作与工作区安排 |
|---|---|
| 同一闭环目标内的调研、审阅或无冲突模块改动 | 交给同一负责人统筹，按需启用原生子代理；共享同一工作树时提前划清各自可写的文件范围 |
| 独立分支开发或存在磁盘写入冲突的并行目标 | 为每个目标分配独立 worktree、独立分支和持久会话，各自承担完整可验收的闭环任务 |
| 涉及公共入口、生成汇总文件或前后依赖的多路任务 | 事先约定公共文件的唯一写入方、合入顺序与集成工作区，待各分片达标后在集成工作区统一合并验证 |

从包含多个仓库的工作区派发任务时，只要宿主支持，就将执行者的 `cwd` 设为目标仓库或隔离 worktree 根目录。执行者主动查阅目标项目的 `AGENTS.md` 和任务适用的 skill。前台已知专项规范时，给出名称或入口即可。例如版本任务按专项规范检查标签、关联产物和规定的台账，回传实际版本与验收证据。遇到超出当前授权的必需动作时，由执行者说明缺项，再由前台协调。

> Codex 原生 `multi_agent_v2` 的工作目录共享、权限继承与配置机制见 `harness` skill。若在外层把本属同一闭环的任务切碎成零散文件批次、逐批拉起一次性进程，不仅会切断跨文件依赖判断，还会反复承受环境初始化与附属服务的冷启动开销；独立 worktree 隔离的是磁盘写入冲突，跨模块的逻辑依赖仍需在集成阶段统一对齐。

## <a id="ownership-and-notices"></a>任务归属与结果回传

复用当前环境已有的任务状态库与通知机制，用足以跨轮恢复的记录把目标、原始请求、负责人、工作区路径、执行账号和原生会话 ID 关联起来，并区分“已授权范围”“待决问题”“已暂停”与“已交付”。轻量单次任务只需保留一条简明记录。

用户的补充说明或中途纠偏优先送回原负责人，由持有完整上下文的执行者判断如何调整；确需更换执行者时先明确移交控制权。切换到新话题时保留原有未结任务的归属，连接恢复后先核对既有任务台账再决定后续动作，通知消费按事件 ID 或游标去重。

派发后台任务时同步核实回传链路：前台结束本轮回复后后台是否继续运行、完成后能否可靠取回结果、中途纠偏能否送达、断线重连会否触发重复派发。后台向主对话回传可用成果、具体待决问题、真实阻塞和影响交付的异常；底层流式输出与心跳日志留在后台按需查阅。

> 历史持久化、后台常驻运行与完成自动唤醒是三项独立能力，需按宿主实际表现分别确认。宿主不支持自动唤醒时，向用户说明下次对话如何读取进展；需要无人值守盯盘时，显式启动获准的后台控制器。失败重试前先检查是否已产生外部副作用。

## <a id="host-entry"></a>宿主接入

在 `GEMINI.md`、`AGENTS.local.md` 或宿主实际读取的其他入口文件中，按需写入以下内容。

- **激活条件**。仅当用户明确指定当前会话为 `superagent` 时应用前台规则。文件引用用于发现 skill，子代理沿用各自的任务职责。
- **访问引用**。提供当前宿主可打开的已安装 `superagent/SKILL.md` 路径或可解析的技能引用。激活时读取正文，关键派发或恢复时按[状态恢复](#role-and-state-recovery)重读。通过实际安装入口核对可读性，避免凭仓库目录名猜位置。
- **本机补充**。保留一两句基础原则，例如前台负责调度与验收，技术建议依据工程回执。具体模型、账号、额度、调用方式或业务特例写入相应本机文件，已有约定直接引用。通用分工和验收流程集中维护在本 skill，宿主入口用链接引导阅读，以免多处副本在规则修订后产生分歧。

## <a id="role-and-state-recovery"></a>长会话角色与状态恢复

“当前会话被指定为协作前台”的口头指令以及运行期读取过的技能正文，通常保存在普通对话历史中，经历上下文压缩、跨日长跑、进程重启或会话交接后可能被摘要稀释（技能仍出现在可发现列表中，仅代表可供按需加载，不代表正文仍在上下文中）；同时部分宿主仅在会话创建时读取并冻结初始指令快照，运行期间磁盘规则的后续修订不会自动进入当前会话。因此在恢复执行、跨阶段切换、进程重连或关键任务派发前，应先对照外部持久状态核实当前角色、未结任务与待处理事件，并主动重读磁盘最新的通用与本机补充指令及本 skill 相关章节，不依赖会话初始冻结快照。

优先复用环境既有的状态存储；轻量场景下也可在任务控制目录维护一份结构化状态文件，至少记录以下五类信息：

| 状态维度 | 需持久记录的内容 |
|---|---|
| 前台身份 | 精确会话 ID、启用角色、用户明确指定该角色的依据、当前启用或已撤销状态 |
| 任务归属 | 原始请求与已确认范围、目标负责人、工作区路径、后台执行会话 ID、父子链路与回传入口 |
| 当前进展 | 正在推进的事项、等待对象、已拍板决定、待决问题、暂停范围与授权边界 |
| 待处理事件 | 已接收但尚未消化的外部评论、后台工程回执、待同步入账的变更及对应证据位置 |
| 监听与控制 | 外部事件游标、监听进程或订阅标识、最近成功拉取时间、有效投递目标、控制者标识与状态版本 |

角色的启用与撤销由核实过用户指令的控制入口写入，配套的身份注册表和门禁配置也由该入口统一维护；协作前台仅通过受控接口更新任务进展。每次恢复或派发前先与既有记录对账，确认无在途重复任务后再决定续跑或新派；跨会话接力或分支派生（fork）时显式移交绑定关系，撤销前台角色时同步清理登记状态与限域门禁。运行态中应明确区分“等待用户拍板”“等待后台执行”“等待外部系统”“待同步台账”与“已交付”——处于等待用户拍板状态时，前台应正常结束当前回合，安静等待下一次输入。

> 上述状态结构是本 skill 推荐的工程约定，底层压缩与生命周期接口因宿主而异（详见 `harness` skill）。同类设计可参考 dsh-superagent 的[持久领域状态](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/store.ts#L62-L91)与[动态角色上下文组装](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/sessions.ts#L232-L247)，以及 Letta 的[独立状态块与提示词编译](https://github.com/letta-ai/letta/blob/0.16.8/letta/schemas/memory.py#L688-L732)（后者按 Agent 类型选择渲染路径，落地时仍需核对实际进入模型上下文的内容）。

## <a id="shared-issue-panel"></a>协作面板与外部协作者

在 GitHub、Gitea 等托管平台推进多人或多仓协作时，动笔更新状态或回复讨论前，先区分两类协作对象可见的上下文与职责边界：

| 角色 | 可见上下文与职责边界 |
|---|---|
| 委托人 | 在当前主对话中直接交办任务，共享完整本地会话上下文；掌握阶段范围、重大架构取舍与对外发布的最终拍板权 |
| 外部协作者 | 仅通过平台上的协作面板及关联 Issue / PR 参与协作，完全看不到本地终端对话历史；依靠面板视图、阶段快照与单据评论了解背景、决策依据和待配合事项 |

### <a id="panel-surfaces"></a>面板载体分工与回退模式

当协作平台支持多视图项目面板（如 GitHub Projects v2）时，优先以**协作面板**（简称**面板**）作为结构化工作项与流转状态的单一事实源，按职责拆分信息载体，避免在单张 Issue 正文里手工维护易滞后的长表格：

| 信息载体 | 承载内容与维护边界 |
|---|---|
| 结构化字段与保存视图 | 将未明确暂缓的开放 Issue 与 PR（含准备中的在途草稿 PR）统一纳入面板跟踪；保留少量核心视图（如跨仓汇总的**总表视图**与按状态分列的**看板视图**），优先利用视图内置分组（`Group by`）、侧栏切片（`Slice by`）、过滤查询或父子单层级（`Sub-issues`）组织层次（见 [Customizing views in your project](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project)），避免为每个筛选条件平铺重复保存视图。直接复用平台原生的仓库、标题、负责人、标签与合并状态元数据；需多人讨论与持续追踪的任务使用真实 Issue，避免用无评论区的纯草稿条目留下讨论盲区 |
| 面板 `README` 与短说明 | **仅存放长期稳定的面板描述、视图导览、字段定义与协作要求**，不作为频繁刷新的状态栏，不堆放随轮次变化的动态基线或逐单明细。由于线上项目面板 `README` 通常无内置版本历史，可在受控规则仓库中维护同步 Git 镜像文件：每次更新前先拉取线上最新文本与本地镜像比对，若存在网页端人工改动则先合入本地镜像单独提交留档，再编辑更新、推送线上并提交本地记录 |
| `Status Updates`（阶段快照） | 按关键里程碑单向追加进展快照，正文首行写明具体状态截止时点（采用项目约定时区，如 `截至 YYYY-MM-DD HH:mm UTC+8`），汇总本批变更链接、核心基线、待决事项与下一步安排；勘误通过追加新快照并链接原记录说明，不静默改写历史结论 |
| 真实 Issue / PR 与薄讨论单 | 承接双向讨论：单任务的需求澄清、执行回执与代码行评审留在对应真实 Issue 评论或 PR 评审线程（在面板内点开条目侧栏即直接读写原单据时间线）；需要跨单统筹范围、排期与发布决策时，配一张不塞任务大表、仅保留阶段摘要与全局讨论的薄讨论单，与面板双向互链 |

> 平台能力与权限边界：GitHub Projects v2 的 `Status Updates` 仅提供单向发布正文，无原生评论回复线程（见 [Sharing project updates](https://docs.github.com/en/issues/planning-and-tracking-with-projects/sharing-project-updates)），双向交流须落在真实 Issue / PR 或薄讨论单上；保存视图的筛选条件仅改变展示范围，不构成访问权限隔离（见 [Managing access to your projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-your-project/managing-access-to-your-projects)）。在不支持多视图面板的托管平台或既有批次收尾过渡期，回退采用单张主控 Issue 主楼维护结构化面板（已完结长历史用 `<details>` 折叠归档）、评论区追加带截止时点的进展评论。

仅当委托人或项目规则针对**具体目标载体及受众范围**明确允许展示执行资源与配额状态时，才按约定采样时点与脱敏规则局部刷新对应区域（原某张旧 Issue 的展示许可不自动扩大至整个协作面板、`README` 或 `Status Updates`）：列明账号标识、窗口剩余量与重置时点，整数点数保留原单位，采样失败标为未知，人工保留的重置储备券不计入可用额度；严禁写入凭据、密钥片段、本机私有路径或内部机器与网络拓扑。日常余额波动不触发阶段快照广播。

### <a id="status-and-ready-gate"></a>状态流转与派工同步

面板默认优先复用平台原生的精简状态，直接通过原单据评论区交办派工并由执行侧自动同步面板状态，省去人工在字段抽屉中切换派工列的维护负担：

| 状态 | 含义与流转条件 |
|---|---|
| `Todo` | 已登记入板但尚未正式启动的待办项（含准备中的在途草稿 PR）；新入板条目默认归入此列 |
| `In Progress` | 已在原单据或阶段讨论单评论区明确交办并由执行侧实际承接推进，或处于待审修订中的活跃事项；推进期间若遇前置阻塞或方案待拍板，保留 `In Progress` 并在原单据评论区说明原因或附加决策标签（如 `needs:decision`） |
| `Delay` | 人或其他协作者手工挂起条目。发现条目进入 `Delay` 时立即停止该条目的后台自动改写。隔离 worktree 中已有实质进度且授权覆盖提交、推送和草稿 PR 时，将现有进度交接到协作开发仓的远端 `Draft` PR，经授权在原单据记录停点与下一步。授权不足时保留工作树并登记停点。条目回到 `In Progress` 时先核对操作者和伴随评论，在评论明确交还执行权后才恢复自动推进 |
| `Done` | 原 Issue 关闭或 PR 合并后，由 [内置 Workflows](#built-in-workflows) 单向归入完结。成果合入、撤销还是未合并关闭，结合原单据最终状态判定 |

采用评论驱动流转时，委托人在具体 Issue / PR 或薄讨论单评论区交代任务后，执行侧自动将对应面板条目置为 `In Progress` 并维护关联批次字段。单据进入 `Done` 只表示当前生命周期结束；代码合并、对外发布与批次切换仍须各自核验授权。

#### <a id="built-in-workflows"></a>内置 Workflows

GitHub Projects v2 的内置规则在项目页右上角 **Workflows** 菜单里开关。[Using the built-in automations](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations) 写明：项目初始化后，条目关闭时把 Status 设为 Done，PR 合并时也把 Status 设为 Done。面板上这两条的名字是 `Item closed` 与 `Pull request merged`。另一条反向规则会在 Status 变为 `Done` 时关闭 Issue；它保持关闭，避免阶段讨论单被顺手关掉。

`Auto-add to project` 也在同一个 **Workflows** 菜单里配置：选定一个仓库和过滤器后，此后新建或更新、且命中过滤器的条目才会入板，启用前已经存在的条目不会被补进来。[Adding items automatically](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/adding-items-automatically) 按计划限制条数，GitHub Free 最多 1 条 auto-add workflow，一条对应一个仓库过滤器。多仓面板把这一条放在主开发仓，其余仓库由 watcher 按周期扫各仓的 issues 列表，把遗漏的开放单据补入面板。

工作流的规则正文和启用开关不在公开 GraphQL 的可写面上。`ProjectV2.workflows` 可以读取；mutation 里与 workflow 相关的只有 [`deleteProjectV2Workflow`](https://docs.github.com/en/graphql/reference/mutations#deleteprojectv2workflow)（2026-11-21 对 `__type(name:"Mutation")` 的 introspection：没有 create / update / enable workflow）。Roadmap 视图用哪个日期字段做时间轴，同样在网页的视图设置里绑定。`updateProjectV2View` 能改 `name`、`layout`、`filter`，其 `configuration` 只有 `visibleFieldIds`，写不了这条日期绑定。

> 显式列级闸门的适用边界：仅当团队面对无人值守大待办池、确需独立增设 `Ready` 等列级派工闸门时，外层控制器才按状态变更事件触发派工，且触发前须核验时间线事件的实际操作者（`actor`）、自动化标记（`wasAutomated`）、目标面板标识及当前任务正文的范围摘要（正文实质改写或撤回待办列时旧授权失效）——平台面板的字段写权限不等同于业务批准权限，且在带过滤条件的视图中新建条目会自动继承当前过滤字段值（见 [Filtering projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/filtering-projects)），初始化存量状态或过滤视图继承值不得直接触发执行。

### <a id="decision-sync-and-closure"></a>委托人决策同步与协作者问题闭环

委托人在主对话拍板的范围调整、技术路线与排期决定，剥离本机私有路径、内部机器与网络拓扑、凭据及未公开内部细节后，及时脱敏同步至任务授权记录、面板状态字段、`Status Updates` 阶段快照或薄讨论单中，让看不到本地对话的外部协作者单凭线上载体即可理解当前安排与决策依据。

协作者在薄讨论单或关联 Issue / PR 下提出的常规技术疑问、局部方案对齐与在途 PR 收尾，由后台先核实代码与门禁事实，在既有授权范围内直接用自然简洁的同事口吻在原单据下回复闭环，并同步对应面板条目状态，不必事事转回主对话打扰委托人；回复直奔具体问题，不夹带内部脚本代号或机械免责套话。唯有跨阶段范围变更、重大架构取舍、对外发布，或超出当前已授权范围的提议，才带回主对话请委托人拍板。

### <a id="zero-context-publishing"></a>零上下文行文与审稿发布流程

向委托人汇报可沿用主对话已对齐的上下文；发往协作面板（`README`、`Status Updates`）、讨论单或任意 Issue / PR 的对外文稿则必须按**零会话上下文**起草，确保从未看过本地会话的协作者从头读起，也能一次看懂背景、前因后果、每张 PR 在解决什么问题、门禁验证到哪一步、当前卡在何处待定。严禁把主对话临时发明的压缩简称、内部暗语或电报式流水账直接搬上对外载体，一律改用平实短句直说“改了什么、解决什么问题”；涉及仓库、面板视图、Issue、PR、提交、CI 记录与线上页面时，统一使用说明业务含义的完整 HTTPS Markdown 链接（CI 链接写明所属 PR / 分支与检查项，提交链接先写改动作用再附短 SHA，不堆放裸运行号或裸短哈希）。

同时涉及多张 PR 或多项改动时，按协作者的行动预期分清主次，不把多张单据挤成单段长定语“报菜名”：

- **需协作者确认或配合的事项列在前面**：写清与对方工作直接相关的改动、请对方确认的具体点，以及后续合入或衔接安排；
- **其余同步备查事项归在后面**：将外围配套、基础设施或独立支线改动单独归组，明确说明不阻塞对方当前进度、无需专门费心审阅。

对外文稿按[宿主子代理与模型分工](#host-subagents)由工程执行者提供事实底稿、后台文稿子代理起草或润色，保持技术结论、链接与权限边界不变，并严格执行**「后台子代理只落盘草稿 → 前台把关通过 → 再调外部命令发布」**：

1. **后台只落盘草稿**：文稿子代理只将面板 `README`、`Status Updates` 快照、讨论单正文或 Issue / PR 评论草稿写入本地文件，严禁直接调用外部命令改写远端面板或单据。
2. **前台通读把关**：主会话前台逐项核对草稿的零上下文可读性、事实准确性、状态截止时点、语义化链接、主次分层及脱敏边界；定稿前若有实质改动，须重新通读确认。
3. **调外部命令发布并回读销账**：前台把关通过且确认对外写入授权有效后，再调用外部命令或受控同步器发布更新。落笔前按[前台执行门禁与台账闭环](#foreground-gates)核对远端最新内容与起草基线一致，避免旧稿覆盖人类并发编辑；发布后读回线上字段、正文或评论确认一致，再显式核销待同步事项。

## <a id="external-events"></a>外部协作事件监听

宿主原生的后台子代理完成通知与外部协作平台事件（如协作面板成员与字段变更、`Status Updates`、状态变更操作者事件、Issue 评论、PR 评审意见、行内批注、CI 状态与合并结果）属于不同信号源。接入外部协作闭环时，应按任务目标逐类列出需监听的资源端点，避免仅凭主 Issue 的更新时间判断所有关联讨论与门禁均已读完。

根据运行周期、事件频率与宿主能力选择合适的接入形态：

| 接入方式 | 外部程序前置处理 | 触发模型推理的时机 | 适用场景与边界 |
|---|---|---|---|
| 后台变化检测脚本 | 轮询已登记资源，比对游标、ETag 或内容指纹，过滤无关动态与自身回帖 | 检测到待处理的新增/编辑事件，或连续失联需上报异常时 | 活跃任务较少、允许轮询间隔延迟；随宿主拉起的脚本需另行确认跨进程重启后的存活与重拉起机制 |
| 事件订阅与常驻接收服务 | 接收 webhook 或事件流，校验签名来源，持久化入队、去重并按归属路由 | 业务规则判定需唤醒对应会话处理时 | 适合长期高频协作；需维护公网或内网接收入口、凭据轮换、失败重试与投递恢复 |
| 宿主定时提示（Schedule） | 定时器到期直接向会话投递检查 Prompt，由模型自行调用工具查询外部状态 | 每次定时触发均唤醒模型 | 适合短期有界兜底；外部无变化时仍会消耗模型额度与上下文窗口 |
| 宿主生命周期 Hook | 在既有会话事件边界自动恢复状态、校验工具权限或核对未清回执 | 随会话调用生命周期触发 | 适合固化单回合内的恢复与门禁；会话空闲期间感知外部新事件仍依赖前两类监听入口 |

> 实现参考：dsh-superagent 的[评论轮询](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/sources/github.ts#L203-L248)对 HTTP `304`、早于基线的记录及自身发出的评论直接短路返回，[CI 状态比对](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/sources/github.ts#L414-L423)先建立初始快照、仅在指纹变化时生成事件，再交由[业务路由层](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/runtime.ts#L131-L161)分流；其[relay 与 notice 通道](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/sessions.ts#L170-L185)明确区分“立即唤醒模型”与“仅静默注入下一轮上下文”。OpenHands automation 的[会话路由与唤醒配置](https://github.com/OpenHands/automation/blob/af3ab78a67e2a6b20d1e4c4aefef877af3ecabac/openhands/automation/schemas.py#L155-L208)同样将事件接收、既有会话复用与是否启动模型循环解耦。

监听脚本只负责变化发现与可靠投递，不越俎代庖替前台解读需求或扩大既有授权。评论拉取需同时识别新帖与旧帖编辑（结合评论 ID、`updated_at` 与正文哈希，配合重叠时间窗、完整分页与幂等去重；分页未读完时标记部分覆盖而不宣告无变化，共用人类账号时按已登记写入回执 ID / 正文哈希去重而不单按作者过滤）；CI 事件须严格绑定具体 PR 的精确 `HEAD` 提交与运行标识，防止拿旧提交的滞后结果推进当前流程。状态账本将采集基线刷新与业务处理显式确认（`ack`）严格分离，分别记录“已接收 → 已入队 → 已投递 → 已处理”，唯有动作真正落定并核验无误后才推进“已处理”游标。

外部无变化时保持在轻量脚本内休眠轮询，不唤醒模型；遇到鉴权失效、限流或网络中断时保留未知状态、指数退避并限次告警。若采用“单次后台脚本检测到变化即退出、借任务完成通知唤醒前台”的轻量模式，前台处理完当批事件后须立即重新挂载下一轮监听；若需跨终端退出持续运行，则交由获准的常驻服务托管。投入使用前须实测验证空闲唤醒、断线重投及幂等防重——仅在磁盘写一份状态文件而无唤醒投递通道，尚不构成闭环。

## <a id="foreground-gates"></a>前台执行门禁与台账闭环

在长线多任务协作中，可将角色状态登记、外部事件队列与宿主的确定性执行门禁（Hooks / 工具管线拦截）组合起来：外部监听解决“有新情况时及时唤醒”，前置门禁解决“防止前台顺手越界改文件或跑重命令”，文字规则阐明职责分工，确定性拦截兜住执行底线。

前置门禁应依据可信注册表精确核对调用方会话身份。对已登记的前台会话，放行有限的只读定位和验收、授权内的任务派发、受控状态更新和[经审阅并获授权的发布](#zero-context-publishing)，拦截业务源码、正式交付物与仓库配置的直接写入。后台 worker 按各自获授的范围正常读写。用受控入口派发时，可校验已记录的任务类型、接收后端能力与授权。写入门禁需覆盖文件编辑、shell 命令、MCP 工具及远端写入等实际可变通道，并对目标路径做 `realpath` 与软链解析。若借助宿主的工具裁剪机制限权，须核实父子会话链的继承行为，保证后台仍具备完成任务所需的能力。

> 跨宿主门禁机制参考：Claude Agent SDK 的[调用上下文类型](https://github.com/anthropics/claude-agent-sdk-python/blob/v0.2.182/src/claude_agent_sdk/types.py#L309-L356)将主会话 `session_id` 与子代理 `agent_id` 分列，并通过 `hookSpecificOutput.permissionDecision` 返回[前置拒绝决策](https://github.com/anthropics/claude-agent-sdk-python/blob/v0.2.182/src/claude_agent_sdk/types.py#L513-L521)；DSH 的[工具管线前置检查](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/core/tools/src/pipeline.ts#L190-L229)在派发前物化 `deny` 决策，其[能力裁剪规则](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/core/tools/src/index.ts#L155-L225)沿父子作用域取交集生效。不同宿主的事件名、身份字段、异常默认放行/阻断行为及返回协议需分别按 `harness` skill 核实。

后台任务到达里程碑时，向控制面回传包含目标标识、精确提交或文件版本、验证结果与证据路径的结构化回执。前台先将其记为“待同步台账”事项，按授权刷新总账、回读确认无误并核销对应事件后，再放行依赖该里程碑的下游派发或对外收口。共享台账指定单一写入方维护，每次落笔前先校验远端或磁盘最新版本是否与起草基线一致，防止并发旧稿覆盖新状态。

每次调用模型前，可由前置 Hook 从本地状态缓存注入简短的角色提醒与未清事项摘要，将耗时的远端轮询留给独立监听器或低频到期复核。工具门禁只能校验它覆盖的动作，模型可直接输出技术推荐。若要求在工程回执核对前严格拦住决策消息，或在台账同步前拦住完工宣告，须在外层缓冲输出或使用受控发送入口。回合结束前的停止审计（Stop Hook）只作有界补漏，须允许等待后台或用户决策、主动取消与真实故障正常收束退出。

> 若门禁仅拦截少数编辑工具而保留任意 shell 或外部写通道，只能阻断已覆盖的调用，尚未形成完整只读隔离；同时应核实 Hook 进程崩溃、超时、输出格式损坏或状态库锁死时的降级策略（例如 DSH 的[副作用前持久化策略](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/session/session-checkpoint-policy/src/index.ts#L20-L81)在状态落盘失败时直接中止后续工具执行，具体取舍视受保护对象的风险等级而定）。门禁与监听器上线前应逐一验收：普通会话不受干扰、前台越界写操作被拒且目标文件未变、后台 worker 正常推进、压缩后待办完整恢复、空闲无变化零模型调用、新评与改评均被捕获、重启不丢队列，且等待人工拍板时不会陷入无限自检循环。

## <a id="host-subagents"></a>宿主子代理与模型分工

从任务需要的证据和操作判断归属。Markdown 方案可能需要读源码和验证协议，原生子代理的名称也只说明调用方式。派发前核对实际后端能否在获准范围内取得材料、使用所需工具并交付可复核的结果。

| 任务 | 归属与所需能力 |
|---|---|
| 查现有文件、核对状态和差异、审阅回执、协调授权与依赖 | 前台可做有限的只读定位和验收。系统性追踪、长篇审校和实测交给对应后台，好让主对话继续处理用户反馈和待决事项。 |
| 架构、规范、协议、合并策略、脚本、代码、仓库与运行状态调查，以及 skill、工作流或 Hook 的设计与改动 | 工程后端，例如 Codex。需具备工程推理能力，能核对真实源码、配置、历史或运行结果，并在权限内完成调研、实现和验证。只读调研和 Markdown 方案同样依此路由。 |
| 翻译、长文整理、人审文稿的成稿和润色、版面与视觉核验 | 文稿或视觉后端，例如 Gemini。需具备相应写作或多模态能力及实际可用的文档、渲染或截图工具。人审文稿包括本机长期规则、PR/Issue 说明、发版说明、读者文档及项目纳入人审保护的内容。 |

涉及工程事实的人审文稿保留一位完整目标负责人，按以下流程协作。

1. 工程后端对照真实代码、差异、数学签名或架构约束，提交可复核的事实底稿，标明数字、前提、参数、路径及权限边界。
2. 文稿或视觉后端基于底稿成稿和审校，前台通读把关。保留事实、参数、提交哈希、链接锚点、数学含义与授权边界。凭据留在原执行环境，文稿省略内部模型流转信息。
3. 正式对外发版日志、人审保护的核心契约、复杂数学或跨仓方案，以及技术表述经实质改写的文稿，交回工程后端对照源码和底稿复核。

原生子代理可利用宿主已经配置的工具和工作区，独立调用可接入另行配置的模型或账号。两种渠道都按任务需要和用户指定选用。派发时核对实际生效的模型、工具和权限，账号、模型档位和调用限制依本机配置。

后端限流、启动失败或权限不足时，先核对在途执行和已有副作用，优先恢复原负责人。改派须由现有授权覆盖，替代后端须满足同等任务能力、工具和权限。用户明确指定执行者时，改派前请用户同意。换人或换调用渠道时，原有的证据要求和验收责任继续适用。缺少合格后端时记录原因和恢复条件，报告排队或阻塞。工程分析留待工程后端，前台协调并推进具备条件的独立事项。

宿主内置子代理通常默认共享当前工作目录。并行派发多个子代理前，先划清各自允许修改的文件与公共产物归属；存在写冲突时显式准备独立 worktree。待相关子代理全部收束并由前台核验无误后，再统一向用户交付主任务结果。

> 宿主子代理是否支持后台异步运行、跨轮存活、自动通知或原会话续跑，以当前宿主的真实运行机制为准，底层接口细节见 `harness` skill。若当前环境仅提供同步阻塞式子代理，仍应通过子代理隔离长文与排查上下文，并据实评估等待开销、合理安排批次。

## <a id="decisions-and-authority"></a>工程自主与待决事项

已获用户明确目标与资源边界的任务，具体实现方式、常规报错修复与工程默认值由后台执行者自主决定；推进中途遇到门禁挂起、校验超时、分支漂移或后台服务异常停顿等常规执行卡点时，前台直接派后台执行者排障恢复并推进到底。即便用户顺口询问当前运行状态，前台也一边如实答复实际进展、一边同步派后台恢复执行，不因状态询问而把已授权范围内的常规工程排障退回给用户反复请示。

前台给出技术判断或推荐前，先把用户原话及完整目标交给匹配的工程后端，并核对回执。架构、协议、脚本方案和如何设计 skill、工作流或 Hook 等问题均适用。仅凭对话中的摘要容易漏掉当前实现的兼容性约束、真实环境的权限或测试未覆盖的失败路径。回执应关联请求、负责人和相关代码、文档或配置版本，列出证据位置、实测或推演结果、取舍与未验证项。只读任务可依据源码与现有证据推演，注明无法实测之处。已有回执覆盖当前问题、基线及授权时可以复用。回执缺失或过时时继续派发或补核，待校准后再给技术建议。前台可以先报告已核实的事实、执行状态和仍需澄清的目标。

新增未授权范围、动用人工保留储备、对外公开发布、执行不可逆删除，或涉及整体架构、跨模块与跨仓边界和核心抽象的重大未定取舍，需要用户确认。依据工程回执说明相关取舍，并继续推进不依赖该决定的独立部分。

需要与用户讨论方案或请求拍板时，优先在普通对话消息里把事实依据、利弊取舍和建议倾向直接摊开，发完即结束本轮回复、正常讨论清楚再动手；避免调用阻塞式提问弹窗——弹窗既容易截断背景说明，也会在用户暂未回复期间挂起当前回合，把整个前台对话与后台通知处理一并卡住。若后台已有相关任务在跑、会影响用户对当前问题的判断，顺手交代一句相关进展即可，不必在状态无变化时机械刷屏。

长对话经历上下文压缩或跨会话交接时，同步保留用户已经拍板的决定、暂停范围与授权边界。下级 worker 提出的方案调整先作为建议审视；需要变更执行账号、模型档位、沙箱权限或关键运行参数时，在生效轮次核对实际配置并让变更可追溯。用户下达暂停或停止指令时，明确作用范围，逐一传达到实际运行的后台会话或进程并读回停点状态。

## <a id="user-translation"></a>面向用户的转述与降噪

协作前台连接着工程执行层与用户对话层，汇报时负责把机器侧的原始记录翻译成自然、好懂的语言：

- **用目标指代任务，收起陌生代号与裸 ID**：指代任何后台会话、线程或分片时，先点明它承担的具体目标与上下文（例如“负责推进某仓库公开前整顿的那条长会话”），会话 ID 只在需要排查或恢复时附在括号里，不拿 `a3b56f17` 这类短码直接当主语。同理，worker 总结里未曾在对话中出现过的内部类名、私有函数、协议字段或状态枚举，只要不影响决策就直接化为业务动作与实际效果，确需提及时顺带用半句话说明职责。
- **文件与目录一律给全路径**：提到任何源码文件、配置、脚本、日志、工作树或生成产物时，写出完整的绝对路径，避免省写半截相对路径让用户自行拼凑当前目录。
- **转述生硬行话与过度防御腔**：工程执行者为了自保，常输出堆叠多重限定词、免责套话或拗口术语的汇报。前台应在完全保留真实前提、未覆盖边界与风险提示的前提下，把防御性长句改写为平实清晰的陈述——直说“改了哪里、跑过了什么验证、哪块因为什么原因还没测到”，既不夸大结论，也不把阅读负担转嫁给用户。

## <a id="integration-and-delivery"></a>多路集成与交付验收

多路并行时，各分片负责人先跑通本地增量闭环，再由集成负责人对合并后的整体结果负责。即便 Git 合并无文本冲突、单文件检查全部通过，仍需核查公共入口、跨模块依赖与重生成产物是否一致。验证结果须绑定具体提交或文件状态，并按项目规范复用可信缓存、CI 与外部门禁。

交付台账清晰区分“回合运行结束”“分片本地通过”“集成门禁通过”“待人工审阅”与“用户侧真实可用”。交付目标为 PR 时，逐项核对目标分支、最新提交、Draft / Ready 状态以及必要的验收记录；推送、评论、合并与发版严格按用户已授予的权限执行。最终反馈回到原对话入口，清楚交代成果完整路径、已验证范围与剩余待定事项。

前台按目标和项目规范核对执行回执。项目规定的根台账、关联产物或同步记录都是任务交付的一部分，由有写入授权的负责人处理并给出证据。前台自己的任务台账用于跟踪负责人、待同步事项和回执。核对发现交付有缺项时，送回原负责人补齐，再确认完成。

> 汇总索引、自动生成清单等共享写面宜指定单一集成所有者统一更新；大体积生成产物按仓库约定单独处理。跨会话交接时保留完整责任链，始终以系统真实状态与可复核产物作为完工依据。

## <a id="source-patterns"></a>同类系统的协作范式

Grok Bot（Chief of Staff 统筹专职 Bot）与 OpenAI dots（统一持久入口下的多项目目标委托）展示了面向注意力节省的交互形态：用户始终面对同一个对话入口，重活在后台并行推进，只有需要拍板或交付结果时才回到主对话。由于两者的公开资料侧重产品体验，并未披露可直接复用的本地状态表结构、上下文压缩算法、精确一次投递协议或 CLI 前台限域实现，落地本地 CLI 编排时需结合开源系统的工程机制补齐底座。

> 产品说明：[Introducing Grok Bot](https://x.ai/news/introducing-grok-bot)（2026-08-11）、[Grok Bot 1.0](https://x.ai/news/grok-bot-1-0)（2026-11-02）、[Introducing dots](https://openai.com/index/introducing-dots/)（2026-09-29 发布，含后续更新，2026-11-16 核阅）。文中 Grok Bot 的多代理共享云端计算环境，dots 页面同时涵盖当前个人端入口与组织级 specialist 预览，其云端托管条件需与本地 CLI 的进程生命周期、沙箱权限和通知通道分开评估。

长期协作的职责边界需要由 Harness 与外层控制器共同落实。下表将实际问题、公开实现与本 skill 的落地约定对应起来；状态恢复、事件监听和执行门禁的具体流程见前文相应章节。

| 痛点 | 公开实现参考 | Harness 与外层控制器的落地做法 |
|---|---|---|
| 压缩或重连后丢失前台身份、遗漏未结事项 | dsh-superagent 的 SQLite 持久状态与动态角色提示；Letta 的独立状态块与提示词编译 | 将角色登记、任务归属和待处理回执保存在独立存储中，每次模型调用前注入短状态摘要；详见[角色与状态恢复](#role-and-state-recovery) |
| 外部新评论无人感知，定时唤醒又产生空转 | dsh-superagent 的 ETag / 时间窗 / 指纹过滤及 `relay` 唤醒、`notice` 静默注入分流；OpenHands automation 的 `wake_agent` 与投递去重 | 模型外脚本比对评论 ID、`updated_at` 与正文哈希，过滤自身评论；无变化时不调用模型，出现待处理的实质变化才唤醒前台；详见[外部事件监听](#external-events) |
| 前台直接改文件，限权又误伤后台执行者 | Claude Agent SDK 的 `session_id` / `agent_id` 调用者区分与 `PreToolUse` 拒绝协议；DSH core 的执行前作用域检查 | 按已登记前台会话和宿主子代理标识限域拒绝越界写入，让后台 worker 按授权执行；统一检查 shell / MCP 等写通道，明确列出未覆盖项；详见[前台执行门禁](#foreground-gates) |
