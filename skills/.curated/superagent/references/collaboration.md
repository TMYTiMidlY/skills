# 目标委派与持续协作

本篇说明目标归属、工作区拓扑、宿主子代理分工、面向用户的转述方式与交付验收流程。直接发起和管理外部 Codex worker 见 [Codex SDK 编排](sdk-orchestration.md)，接管存量 CLI 会话见[存量 CLI 会话的旁路监控与推进](cli-monitoring.md)。

## <a id="goals-and-workspaces"></a>目标委派与工作区划分

委派材料直接保留用户的原始请求、必要背景、已确认的权限边界和交付位置。原始材料可直接附入，或提供执行者确实可读的路径与链接；前台只补充跨任务约束，把实现路线、验证方式和内部子任务拆解留给目标负责人决定。

例如，用户提出“做一个 2D 鹈鹕骑自行车的 HTML”，就把这句话原样传给执行者，只补上允许写入的目录与最终文件路径；动画算法、交互细节和结构组织全部交给执行者自行拍板。目标负责人也可在自身权限内调动原生子代理并行处理子问题。

根据磁盘写入冲突面和集成关系安排工作区拓扑：

| 任务关系 | 协作与工作区安排 |
|---|---|
| 同一闭环目标内的调研、审阅或无冲突模块改动 | 交给同一负责人统筹，按需启用原生子代理；共享同一工作树时提前划清各自可写的文件范围 |
| 独立分支开发或存在磁盘写入冲突的并行目标 | 为每个目标分配独立 worktree、独立分支和持久会话，各自承担完整可验收的闭环任务 |
| 涉及公共入口、生成汇总文件或前后依赖的多路任务 | 事先约定公共文件的唯一写入方、合入顺序与集成工作区，待各分片达标后在集成工作区统一合并验证 |

> Codex 原生 `multi_agent_v2` 的工作目录共享、权限继承与配置机制见 `harness` skill。若在外层把本属同一闭环的任务切碎成零散文件批次、逐批拉起一次性进程，不仅会切断跨文件依赖判断，还会反复承受环境初始化与附属服务的冷启动开销；独立 worktree 隔离的是磁盘写入冲突，跨模块的逻辑依赖仍需在集成阶段统一对齐。

## <a id="ownership-and-notices"></a>任务归属与结果回传

复用当前环境已有的任务状态库与通知机制，用足以跨轮恢复的记录把目标、原始请求、负责人、工作区路径、执行账号和原生会话 ID 关联起来，并区分“已授权范围”“待决问题”“已暂停”与“已交付”。轻量单次任务只需保留一条简明记录。

用户的补充说明或中途纠偏优先送回原负责人，由持有完整上下文的执行者判断如何调整；确需更换执行者时先明确移交控制权。切换到新话题时保留原有未结任务的归属，连接恢复后先核对既有任务台账再决定后续动作，通知消费按事件 ID 或游标去重。

派发后台任务时同步核实回传链路：前台结束本轮回复后后台是否继续运行、完成后能否可靠取回结果、中途纠偏能否送达、断线重连会否触发重复派发。后台向主对话回传可用成果、具体待决问题、真实阻塞和影响交付的异常；底层流式输出与心跳日志留在后台按需查阅。

> 历史持久化、后台常驻运行与完成自动唤醒是三项独立能力，需按宿主实际表现分别确认。宿主不支持自动唤醒时，向用户说明下次对话如何读取进展；需要无人值守盯盘时，显式启动获准的后台控制器。失败重试前先检查是否已产生外部副作用。

## <a id="host-subagents"></a>宿主子代理与模型分工

按任务擅长领域分配执行模型：重代码编写、跨模块改造、编译测试与底层排障优先派给 **Codex**（默认使用 `gpt-6.1-sol` 与 `xhigh` 档位）；纯文字起草、材料归纳、语言润色与面向用户的解释转述优先交给 **Gemini** 模型处理。

当用户明确指定“由你自己完成”，或任务无需跨进程启动外部 worker 时，直接使用当前宿主自带的后台子代理承接耗时调研、编码或验证。主对话传递完整目标与背景、登记完成通知，继续保持对话响应并负责最终整合与润色。

宿主内置子代理通常默认共享当前工作目录。并行派发多个子代理前，先划清各自允许修改的文件与公共产物归属；存在写冲突时显式准备独立 worktree。待相关子代理全部收束并核验无误后，再统一向用户交付主任务结果。

> 宿主子代理是否支持后台异步运行、跨轮存活、自动通知或原会话续跑，以当前宿主的真实运行机制为准，底层接口细节见 `harness` skill。若当前环境仅提供同步阻塞式子代理，应据实评估等待开销并合理安排批次。

## <a id="decisions-and-authority"></a>工程自主与待决事项

在用户已授权的范围内，具体实现方式、常规报错修复与工程默认值由执行者自主决定。涉及整体架构取舍、仓库规范调整或高风险外部操作等尚未定论的事项，继续保持为待决状态：先推进不依赖该决定的独立部分，同时收齐实测证据、影响范围与可行选项。

需要与用户讨论方案或请求拍板时，优先在普通对话消息里把事实依据、利弊取舍和建议倾向直接摊开，发完即结束本轮回复、正常讨论清楚再动手；避免调用阻塞式提问弹窗——弹窗既容易截断背景说明，也会在用户暂未回复期间挂起当前回合，把整个前台对话与后台通知处理一并卡住。若后台已有相关任务在跑、会影响用户对当前问题的判断，顺手交代一句相关进展即可，不必在状态无变化时机械刷屏。

长对话经历上下文压缩或跨会话交接时，同步保留用户已经拍板的决定、暂停范围与授权边界。下级 worker 提出的方案调整先作为建议审视；需要变更执行账号、模型档位、沙箱权限或关键运行参数时，在生效轮次核对实际配置并让变更可追溯。用户下达暂停或停止指令时，明确作用范围，逐一传达到实际运行的后台会话或进程并读回停点状态。

## <a id="user-translation"></a>面向用户的转述与降噪

协作前台连接着工程执行层与用户对话层，汇报时负责把机器侧的原始记录翻译成自然、好懂的语言：

- **用目标指代任务，收起陌生代号与裸 ID**：指代任何后台会话、线程或分片时，先点明它承担的具体目标与上下文（例如“负责推进某仓库公开前整顿的那条长会话”），会话 ID 只在需要排查或恢复时附在括号里，不拿 `a3b56f17` 这类短码直接当主语。同理，worker 总结里未曾在对话中出现过的内部类名、私有函数、协议字段或状态枚举，只要不影响决策就直接化为业务动作与实际效果，确需提及时顺带用半句话说明职责。
- **文件与目录一律给全路径**：提到任何源码文件、配置、脚本、日志、工作树或生成产物时，写出完整的绝对路径，避免省写半截相对路径让用户自行拼凑当前目录。
- **转述生硬行话与过度防御腔**：工程执行者为了自保，常输出堆叠多重限定词、免责套话或拗口术语的汇报。前台应在完全保留真实前提、未覆盖边界与风险提示的前提下，把防御性长句改写为平实清晰的陈述——直说“改了哪里、跑过了什么验证、哪块因为什么原因还没测到”，既不夸大结论，也不把阅读负担转嫁给用户。

## <a id="integration-and-delivery"></a>多路集成与交付验收

多路并行时，各分片负责人先跑通本地增量闭环，再由集成负责人对合并后的整体结果负责。即便 Git 合并无文本冲突、单文件检查全部通过，仍需核查公共入口、跨模块依赖与重生成产物是否一致。验证结果须绑定具体提交或文件状态，并按项目规范复用可信缓存、CI 与外部门禁。

交付台账清晰区分“回合运行结束”“分片本地通过”“集成门禁通过”“待人工审阅”与“用户侧真实可用”。交付目标为 PR 时，逐项核对目标分支、最新提交、Draft / Ready 状态以及必要的验收记录；推送、评论、合并与发版严格按用户已授予的权限执行。最终反馈回到原对话入口，清楚交代成果完整路径、已验证范围与剩余待定事项。

> 汇总索引、自动生成清单等共享写面宜指定单一集成所有者统一更新；大体积生成产物按仓库约定单独处理。跨会话交接时保留完整责任链，始终以系统真实状态与可复核产物作为完工依据。

## <a id="source-patterns"></a>同类系统的协作范式

dsh-superagent 将节省人的注意力置于首位：路由层原样转发用户请求，交由下级 worker 完成代码调研与实现；后续追问自动路由给既有负责人，关键进展与待决问题回流至发起会话，并由持久投递和等待上限保障前台及时结束回合。

> 一手源码：[注意力成本与职责划分](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/000-philosophy.md#L3-L15)、[前台交互与结果回流](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/prompts/orchestrator.md#L1-L16)、[原始请求转发与未决授权](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/prompts/dispatch.md#L31-L51)、[前台等待上限](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/sessions.ts#L63-L85)、[持久化消息投递](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/effects.ts#L57-L71)。该原型中限制路由附言字数、固定目录布局及禁止前台直接读代码等做法属于其特定实现取舍；本 skill 保留前台做轻量核查、纯文字工作与面向用户转述的弹性。外层目录与命令包装仅提供默认环境，合并放行仍依赖独立门禁，见[执行环境与合并边界](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/003-execution.md#L78-L90)。

Grok Bot 展示了常驻在线的多代理协作形态：由 Chief of Staff 统筹多个专职 Bot、同步上下文，并在真实工具环境中推进工作；OpenAI dot 则围绕统一持久入口组织目标级委托与多项目并行，让用户在后台运转期间随时讨论和调整方向。本 skill 吸收上述协作体验，具体后台与通知能力按当前宿主实测为准。

> 官方说明：[Introducing Grok Bot](https://x.ai/news/introducing-grok-bot)（2026-08-11）、[Introducing dots](https://openai.com/index/introducing-dots/)（2026-09-29）。文中 Grok Bot 的多个代理共享云端计算环境，Dots 页面同时包含当前个人端能力与远期团队设想，均不代表不同宿主具备相同的底层隔离或调度实现。

独立派发的后台任务通常只能看到显式传入的上下文，且可能在前台对话暂停后继续运行；前台在转发补充信息或执行暂停指令时，应逐一覆盖到真正干活的下级会话。

> [Getting started with your dot](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot)（2026-11-14 核阅）指出独立启动的 Work / Codex 任务可在主入口暂停后继续运行；其他宿主的传播与停止语义需按各自实现核实。
