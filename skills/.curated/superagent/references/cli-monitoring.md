# 存量 CLI 会话的旁路监控与推进

本篇用于接管并非由当前 SDK 控制器发起的 Codex CLI / TUI / `exec` 长会话：先从磁盘 rollout、后台服务与工具进程旁路观察真实进展，再在用户授权范围内通过队列投递或无头恢复推进任务。由前台直接新建和管理 worker 时，优先采用 [Codex SDK 编排](sdk-orchestration.md)。

> rollout 事件结构、`codex queue`、`codex exec resume`、写锁机制、goal 生命周期及 `token_count` 限流字段由 `harness` skill 维护。磁盘旁路观察看到的是已落盘的持久切面，队列投递亦受存活写者约束，实际控制确定性低于原生 SDK 连接。

## <a id="session-ownership"></a>会话定位与控制权交接

接手前先查清目标会话的 `thread_id`、实际生效的 `CODEX_HOME`、工作目录、分支、托管 daemon、当前活动回合以及派生的工具子进程，并将其登记回[任务归属与结果回传](collaboration.md#ownership-and-notices)。历史排查统一走只读方式；发起推进前确认目标已获授权、当前无人工暂停指令，且同一时刻只有一个控制者操作该会话。

tmux 等终端复用器只承载外层界面，需将界面进程、后台 daemon 与长时工具进程分开核查：终端关闭后 daemon 仍可能在后台继续跑轮次，也可能虽已空闲却仍占着线程写锁。涉及跨账号接管恢复时，先按 `harness` skill 检查共享存储软链、子代理树、未结 goal、滞留队列与实际执行账号。

> 共享 daemon 上可能同时托管着其他无关会话，执行终止、归档或强制释放写锁前须核清影响范围；直接打开旧 TUI 还可能触发恢复历史 goal 的默认提示，只读查阅与启动执行应严格分开。

## <a id="silence-and-progress"></a>静默窗口与长工具判读

综合 rollout 最新事件、文件最后写入时间、在跑长时工具（如整包编译、形式化证明器、长测试套件）与工作树新产物判断会话是否健康推进：近期持续有落盘输出且无报错时保持观察；静默时长超出该类任务的合理区间时，先检查子进程 CPU / I/O 与工具输出，确认真已停滞后再介入恢复。

> Codex `0.15x`–`0.162` 的多日长任务盯盘曾采用“5 分钟内有写入不打扰、超过 10 分钟无写入先查长时子进程”的经验窗口，实际阈值随构建与验证耗时调整。长工具执行期间 rollout 完全静默属于正常现象，而 `task_complete` 事件也仅代表单轮结束而非整个目标完工。

遇到异常中断时，结合 `token_count` 中的限流遥测与具体报错文本区分“窗口配额耗尽”“模型服务端拥塞”“网络抖动”与“凭据失效”。确认触发窗口限流后按 `resets_at` 时间退避；`codex queue` 只负责缓存待投递输入，到点唤醒仍需依靠获准运行的后台监控或下一次明确恢复动作。

## <a id="delegation-deadlock"></a>委派死锁与明确推进指令

若单轮正常结束（出现 `task_complete`）但目标仍未交付，检查主线程结语、子代理状态、待验产物与下一步责任归属。常见卡点是父线程发完任务等着子代理“复核”，子代理又停下来等父线程“确认”，双方互相礼让形成假待命死锁；此时应直接把下一步动作指定给具备完整上下文与写权限的负责人。

当单纯发送“继续”无法打破互等时，改为投递边界清楚的明确指令：点明剩余未完成的目标、由当前主负责人亲自收拢既有改动、哪些门禁验证或提交动作已在授权范围内，以及完成后需回传哪些证据。属于工程内部的排错阻塞优先交由原负责人闭环消化。

> 现场排障中曾用“不要继续向下委派，由当前主线程亲自完成剩余门禁验证及已获授权的提交推送”直接解开循环等待。此类指令仅用于消除既有授权范围内的委派死锁，绝不能凭空推导出新的提交、推送或发布授权。

## <a id="delivery-and-resume"></a>队列投递与无头恢复

投递消息前先核实原后台服务是否仍持有该会话：原写者存活且可接收输入时，优先使用 `codex queue` 无抢占排队；会话已卸载或原控制进程已失效时，在理清写锁与残留子进程后改用获准的 `codex exec resume` 无头恢复，或交由 SDK `thread_resume` 接管。每次投递后回到队列记录与 rollout 新增轮次核实消息确已进入模型上下文，将“入队成功”与“实际开跑”分开记录。

> `codex queue` 写入成功仍依赖存活 writer 消费才能真正触发新轮次；`codex exec resume` 则可能将此前滞留的队列消息连同新提示词一并送入，或在旧写锁未释放时报错退出。底层状态码与版本差异见 `harness` skill。

无人值守盯盘放在后台低频运行，只向主对话汇报实质性进展、真实阻塞或需要用户拍板的事项。每轮巡检围绕新增事件、新提交或限流重置时间收集增量证据；触发异常恢复后确认会话确已向前推进，持续跟进直至达到约定的交付标准。

> 早期监控记录中曾观察到反复执行完全一致的轮询 shell 命令偶发触发工具侧的“无进展”拦截，通过交替使用不同等价写法可绕开（现场观察，尚未在开源代码中定位对应实现）；稳妥做法是依靠合理的后台休眠间隔与真实的增量状态检查判断进展。
