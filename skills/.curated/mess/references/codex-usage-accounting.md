# Codex 夜间会话的用量与额度归因

## <a id="overnight-quota-attribution"></a>Terra 与历史 Sol 的夜间用量核算

> 2026-10-29 实测；目标 Codex CLI 0.165.0，历史 Sol 对照为 0.164.0；额度历史由 DSH Provider Hub 0.7.9 采集，辅助会话读取器为 asmgr 0.6.0。本文保存脱敏后的聚合结果和排查方法：目标账号称 A，对照账号称 B，不保留真实账号别名、邮箱、身份 ID、会话 ID、主机名、私有项目身份或绝对路径。时间统一为 UTC+08:00。

### 现象与核查范围

一个持续研究的 Terra 会话运行约一夜后，账号周额度已用比例升至 85%。操作者记得以前 Sol 运行一夜大约只消耗 10%，因此希望确认运行时长、子代理数、总 token，以及是否因为大量子代理而增加了额度消耗；随后又追问 API 等价费用，以及长上下文的计费分界是否已经改成 500K。

固定目标统计窗口为 **2026-10-29 01:28:38—11:45:00**。截止时父会话仍在收尾，本文记录的是运行中快照，不是最终结束账单。另一台机器的 Sol 历史没有读取；历史对照只来自同一台机器。

需要分别回答三个问题：会话树实际产生了多少用量、账号同期减少了多少额度、按公开 API 价格映射这些 token 约值多少钱。它们使用不同证据，分别报告。

### 证据与读取边界

| 数据源 | 用途 | 边界 |
| --- | --- | --- |
| Codex 的只读 SQLite 会话索引 | 定位工作区、rollout、模型与父子关系 | 账号可能在会话期间切换；创建时身份及索引的最终模型不足以认证整段历史路由 |
| rollout 中的 `session_meta`、`turn_context` 与活动事件 | 复核模型、开始时间、活动回合与工具调用 | 会话存在或最后写入，不等于持续生成；`task_complete` 只认证该回合结束 |
| rollout 中的 `token_usage_record` | 按响应汇总实际记录的输入、缓存输入、输出与推理 token | 只覆盖已记录用量的响应；未记录的失败请求、重试及其他服务费用不补造 |
| Provider Hub 的 `quota-history.jsonl` | 对照同一账号的额度小时曲线 | 是账号级采样，不含请求、会话或工作区归属 |
| rollout 的 `token_count.rate_limits` | 补齐靠近统计起止的额度点、窗口长度及重置时间 | `primary` 与 `secondary` 是字段位置，窗口类型须按时长识别 |
| 官方公开文档 | 核验 API 价格、上下文窗口与订阅规则 | 价格及产品规则会变；下文保存核对日的关键文本，在线链接作为继续查阅入口 |

> 路径按当前配置解析。rollout 通常位于 `$CODEX_HOME/sessions/`，SQLite 位置可能由 `sqlite_home` 单独指定；多个账号可以共用索引。Provider Hub 历史位于 `${DSH_HOME:-$HOME/.dsh}/dsh-provider-hub/quota-history.jsonl`。原始数据可能含邮箱、身份 ID、提示词和私有路径，留在本地；对外只输出白名单字段及匿名聚合。

本次对 Codex 与额度数据只读取证，没有为核算启动新的 Codex 研究或生图请求，也没有刷新登录、修改模型或改变运行中的研究任务。分析助手自身的模型调用与被分析的研究树分开处理。工具使用细节交由 asmgr skill；这里记录核算口径及其限制。

### 会话树与用量核算

先沿父子边递归取得目标树，再对每个 rollout 的用量记录检查 `thread_id`，以 `response_id` 去重，只计入固定截止时间之前的响应。每个线程逐次 `usage` 的和与该线程截止时最后一条 `thread_token_usage` 对账。本案 **240 个线程全部一致、响应 ID 无重复、计入记录无 JSON 解析缺损**。

缓存输入已经包含在 `input_tokens` 中；推理 token 已经包含在 `output_tokens` 中。分别以 `input_tokens - cached_input_tokens` 取得非缓存输入，以 `input_tokens + output_tokens` 取得总量。

> 子会话可能带有父会话历史，因此预防性过滤仍然必要。本案没有发现需要剔除的异线程 `token_usage_record` 或重复响应；不能把通用风险写成这次实际发生了 token 重计。周期性 `token_count` 中的累计数也不逐条相加。

| 范围 | 输入，含缓存 | 缓存输入 | 输出，含推理 | 总 token |
| --- | ---: | ---: | ---: | ---: |
| 父会话 | 1,268,975,117 | 1,264,426,368 | 602,953 | 1,269,578,070 |
| 子会话合计 | 2,241,209,473 | 2,223,610,112 | 2,071,251 | 2,243,280,724 |
| 全树 | **3,510,184,590** | **3,488,036,480** | **2,674,204** | **3,512,858,794** |

全树非缓存输入为 **22,148,110**，输入缓存命中率为 **99.369%**；输出中的推理 token 为 **704,864**。共有 **13,189 次有用量记录的模型响应**，其中父会话 4,776 次、子会话 8,413 次。子会话占总 token 的 **63.86%**，这是 token 占比，不是订阅额度的逐请求分账。

目标窗口墙钟时长为 **10 小时 16 分 22 秒**。父会话活动回合区间合计约 10.26 小时，子会话活动回合区间合计约 16.05 agent·小时；后者可并行，不能当作墙钟时长或模型纯生成时间。

### 子代理数量与协调活动

父会话累计创建 **239 个不同子代理**，均为直接子级；实际活动回合并发峰值为 **3 个子代理**，连同父代理最多 4 个。创建调用共有 244 次，其中 5 次因代理路径已存在而拒绝，未生成额外线程；已有任务续接调用为 228 次。

> 辅助读取器曾把子会话的起点落到父历史的早期时间，显示 239 的区间重叠峰值。按各子会话实际 `task_started` 到 `task_complete`／中止的区间重新计算后，峰值为 3。这个结果只说明本样本中的读取口径偏差，不认证其他版本的表现。所用 asmgr 0.6.0 也不支持较新说明中的 `--turn`、`--tail` 和 `plain`，需先看已安装版本的帮助。

截止快照，各子会话最后一个活动回合均记录为 `task_complete`；这不认证所有会话或进程已关闭。父会话仍有后续收尾工作。

父会话的实际工具调用包括：

| 调用类别 | 次数 |
| --- | ---: |
| `wait_agent` | 1,347 |
| `send_message` | 443 |
| `followup_task` | 228 |
| `list_agents` | 73 |
| 执行包装器调用 | 2,096 |
| 其中包含 `write_stdin` 的进程输出检查 | 756 |

这些动作中包含正常的等待、协作、构建与验收，不能整批认定为无效工作。按用量记录前最近的工具类别做粗分类，与等待子代理、进程输出检查相邻的响应约占父 token 的 47.77%、全树 token 的 17.26%；这是时间相邻的诊断指标，不是可直接删除的成本，也不是已证明的额度归因。

Hub 自身观察到 **16%→82%，增加 66 个百分点**；加入原生起止点，目标窗口的账号差分约为 **69 个百分点**。开跑前的 16% 留作历史基线，85% 是账号累计已用比例。平均增加约 **6.72 个百分点／小时**，整体较平稳，但仍是离散且按整数百分比报告的采样，不是精确的匀速计费轨迹。

Hub 前点比开始早 12 分 45 秒，末点比截止早 33 分 03 秒；内部相邻采样最大间隔为 1 小时 1 秒。空档保留为未知，最后 3 个百分点来自原生遥测，不写成 Hub 已采到 85%。该次核查的 828 条 Codex 历史均只有 `weekly`，没有 `short`、窗口长度或重置时间。

> Provider Hub 0.7.9 的 `lib/quota.js` 中，`recordProvider` 只持久化采样时间、提供方、账号及可选身份标识、采样周期、`used`、credits 与 plan；`lib/quota-core.js` 按时长划分 short／weekly／monthly。历史没有保存完整内存 snapshot。本案原生窗口为 10,080 分钟、`secondary` 为 null，下一次重置为 2026-11-04 14:35:52；这些信息来自原生遥测，不是从 Hub 历史推算。

该账号的 credits 始终显示 0，表示观察到的余额状态，不能据此推出实际现金账单或证明完全没有其他费用。

账号归因需同时保留下列边界：

- 其他账号当夜也有用量，核算按身份分开，未跨账号累加百分比。
- 本机索引未发现创建身份相同、在该时段更新的其他非子代理主会话；这支持本树是主要本机来源，但会话期间切换账号、其他设备、其他客户端或历史 DSH 路由仍可能不被这项筛选覆盖。
- Hub 没有请求级归属，69 个百分点是账号差分；将其主要归给本树是有本机证据支持的估算，不是精确分账。
- `plan: pro` 没有给出账号当时的 5x／10x／20x 等完整档位及历史变更，不能据此认证不同账号拥有相同的周预算。

### 历史 Sol 的同长度窗口

找到同机 **2026-10-27 01:28:38—11:45:00** 的 `gpt-6.1-sol / high` 对照。统计同样沿完整父子树汇总，精确 token 对照使用的记录没有解析缺损。

| 指标 | 历史 Sol，对照账号 B | 目标 Terra，账号 A |
| --- | ---: | ---: |
| 会话树累计子代理数 | 3，期间复用既有代理 | 239 |
| 有用量记录的模型响应 | 2,212 | 13,189 |
| 父 token | 340,155,406 | 1,269,578,070 |
| 子 token | 212,573,819 | 2,243,280,724 |
| 全树 token | 552,729,225 | 3,512,858,794 |
| 输入缓存命中率 | 98.31% | 99.37% |
| 输出 token | 1,982,447 | 2,674,204 |
| 其中推理 token | 802,681 | 704,864 |
| 对应账号周用量 | 22%→40%，增加 18 个百分点 | 16%→85%，增加 69 个百分点 |

响应数约为对照的 **5.96 倍**，总 token 约为对照的 **6.36 倍**，输出却只多 **34.9%**；Terra 父 token 本身也是 Sol 父 token 的约 3.73 倍。输入缓存命中率没有下降，故本样本不支持以缓存失效解释增量。更符合记录的描述是：Terra 这轮进行了更多、输出较短的模型步骤，同时反复携带大段缓存上下文。

两组均按上述固定窗口折算，模型响应频率约为 Sol 3.6 次／分钟、Terra 21.4 次／分钟；每次响应平均输出约为 896 与 203 token。含等待和工具时间的全树平均输出吞吐约为 54 与 72 token／秒。这些值描述整个任务树的墙钟吞吐，不能当作单模型流式生成 TPS 或证明 Terra 的解码速度高出六倍。

> 这是不同日期、账号与任务的观察性对照，代理策略、任务难度、模型行为及套餐都未受控。旧历史中还出现过 used 回落且 `resets_at` 改变的区段；连续身份或窗口未核清前，末尾显示 9%／10% 不足以代表整夜只消耗这些额度。回落的原因本案未定，不统一解释成自然重置或切号。另一台机器的“一夜约 10%”经验仍未验证。

### API 等价费用与订阅摊销

2026-10-29 核对的 Terra Standard 文本价格如下，单位为美元／百万 token：

| 单次请求输入长度 | 非缓存输入 | 缓存输入 | 输出 |
| --- | ---: | ---: | ---: |
| ≤272,000 | 1.00 | 0.05 | 5.00 |
| >272,000 | 2.00 | 0.10 | 7.50 |

> 价格日期快照来自 [Terra 模型文档](https://developers.openai.com/api/docs/models/gpt-6.1-terra.md)及 [API 定价文档](https://developers.openai.com/api/docs/pricing.md)。关键原文为：“Prompts with more than 272K input tokens are priced at 2x input and cache rates and 1.5x output for the full request.” 在线页未提供本次核对可用的版本化 permalink；以上表格和引文保存本案核对日口径，后续核算应重新读取当日规则。`high` 推理强度不等于 Fast 速度档。

按每次响应的输入长度判定分档，以 `非缓存输入 × 输入价 + 缓存输入 × 缓存价 + 输出 × 输出价` 汇总：

| 分组 | 响应数 | 非缓存输入 | 缓存输入 | 输出 | 估算美元 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ≤272K | 6,520 | 10,856,949 | 1,115,450,752 | 1,297,818 | 73.1185766 |
| >272K | 6,669 | 11,291,161 | 2,372,585,728 | 1,376,386 | 270.1637898 |
| 合计 | 13,189 | 22,148,110 | 3,488,036,480 | 2,674,204 | **343.2823664** |

按费用类别合计，非缓存输入约 $33.44、缓存输入约 $293.03、输出约 $16.81。若把所有请求都套短上下文价，会得到约 $209.92，低估约 $133.36。

这是在相同用量、缓存命中及 Standard 价格假设下的 **API token 等价估算**。Codex 记录中的 cache-write 用量为 0，而官方说明 Codex credits 没有单独的 cache-write 费用；这不能认证 API 的缓存写入也免费。因此上述值未另计潜在 API 缓存写入、工具费用、税费及改变运行环境后的缓存差异，不是实际 API 账单或严格上下界。官方当日 Flex／Batch token 单价为 Standard 的一半，形式上约为 $171.64，但时延及任务组织方式不同，不作为本次交互式研究的等同替代。

订阅摊销另按“每周成本为月费四分之一”的指定假设计算。设月费为 P，则本轮摊销为 `P ÷ 4 × 0.69 = 0.1725P`：

| 假设月费 | 假设每周成本 | 本轮摊销 | Standard API 等价金额／摊销 |
| --- | ---: | ---: | ---: |
| $200 | $50 | $34.50 | 约 9.95 倍 |
| $100 | $25 | $17.25 | 约 19.90 倍 |

月费 $200 时，可表述为这轮订阅摊销约相当于 Standard API 估算的十分之一；按同一负载线性外推，满周额度约对应 $497.51 的 API token 等价金额。这里既未确认目标账号的实付月费与完整倍率档位，也未承诺未来每周的兑换比例；摊销不是新增扣款，月费除以四也是比较假设，不是按自然年周数精确分摊。

### 500K、API 分界与订阅规则

对“是否改成 500K”的追问，核查得到三个不同口径：

| 对象 | 2026-10-29 读取的公开规则 |
| --- | --- |
| GPT-6.1 Sol 在 Codex／ChatGPT Work | 默认上下文窗口为 500,000 token |
| GPT-6.1 Sol 使用订阅内额度 | 在 Codex／ChatGPT Work 没有长上下文附加费 |
| GPT-6.1 Terra API | 仍按 272K 输入区分长短价格；模型总上下文窗口为 1,050,000 |

> 日期快照：[模型说明](https://learn.chatgpt.com/docs/models.md)原文为“GPT-6.1 Sol uses a default context window of 500,000 tokens in Codex and ChatGPT Work.”；[订阅定价说明](https://learn.chatgpt.com/docs/pricing.md)原文为“GPT-6.1 Sol usage drawn from your subscription has no long-context surcharge in Codex or ChatGPT Work.”；Terra API 的分界见上一节保存的官方原文。链接为持续更新的阅读入口，所引文字只认证核对日的页面。

Sol 的默认窗口、Terra 的 API 加价分界与订阅内额度是三个独立条件。Sol 的订阅豁免也是分析历史额度差异时应考虑的因素；本案没有找到足够公开说明确认 Terra 订阅是否享有同样豁免，既不能认定 Terra 订阅一定按 API 的 272K 加价，也不能把 API 单价直接换算成周额度扣减规则。

### 归因结论与后续检验

**已核实的结果**是目标树产生约 35.13 亿 token，缓存输入占输入约 99.37%，账号同期周用量增加约 69 个百分点。与找到的 Sol 夜间样本相比，目标树的模型响应约为对照的六倍、输出只多约三分之一，且父会话有显著的协调与状态检查活动。

**有证据支持的解释**是：子代理自身的请求，以及父代理为创建、协调、续接和检查它们产生的更多步骤，都是本轮用量的组成部分。累计 239 个子代理需要和峰值并发 3 个分开理解；子代理数量不是独立、充分的成本指标。更密集的短步骤、大上下文复读、模型行为与订阅规则差异，都可能影响最终额度。

**尚未证明的机制**包括：每个子代理存在固定附加倍率、63.86% 的 token 对应同样比例的周额度、去掉子代理就能节省某个确定的百分点、全部协调动作无效，以及 Terra 在相同负载与套餐下必然比 Sol 更耗额度。缺少的证据是请求级额度分账，或同账号、同窗口规则、同任务、同模型强度与速度档的受控比较。

原分析应保留以下修正：

- 对子代理历史重计的担忧经去重核验排除，不能作为本案根因；活动并发则确实需要从辅助工具的区间结果重新核算。
- 69 个百分点来自账号起止差分；Hub 单独只覆盖其中 66 个百分点，开跑前的 16% 不归本轮。
- “子代理多”需要展开为直接请求和父侧协调负担，不写成已定位唯一根因。
- “token rate”分别说明 API 单价、模型流式 TPS、全树墙钟吞吐与请求频率；本案未测单模型 TPS。
- API 的长上下文价格和 Sol 的订阅豁免分开报告，后者是先前解释额度差异时遗漏的重要条件。

后续若获授权验证，可在同一账号和连续额度窗口内，对相同有界任务比较单代理与少量可复用子代理，固定模型、强度、速度档和上下文策略，并同时记录请求用量、活动区间、缓存、额度及任务产物质量。减少短间隔检查、让子任务执行更完整后再回报，是值得检验的优化建议；本案没有执行该干预，也没有证明减少这些动作后的实际节省额。
