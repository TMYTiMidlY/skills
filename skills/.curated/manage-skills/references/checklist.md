# skills 的要求（检查清单）

每个 skill 应满足的要求，逐条可核对，是"写 / 改 / 审查 / 重构 skill"共同的准绳——**这里是唯一出处**，别在 SKILL.md 或别的 skill 里重抄这些规则，要提就写 skill 名 + 条目名指过来。写作时照着做；**审查**（跨 skill 合规扫描）逐条核对，另加 [review.md](review.md) 的跨 skill 专项检查；**重构**（打磨单篇文档）拿它当诊断项。两条流程本身——审查的"只审不改 / 确认范围 / 输出格式 / 批量修复确认点"见 [review.md](review.md)、重构的"先出改后大纲再动手"见 [refactor.md](refactor.md)。

- **概念优先、说人话**
  - 先讲"是什么 / 为什么 / 解决什么问题"，再给细节；术语黑话只在影响理解时才解释。
- **命令 / 示例优先**
  - 能贴可直接套用的 compose / 配置 / 脚本 / 命令就贴（敏感值留占位符），胜过大段散文。
- **踩坑 / 排障紧贴主题**
  - 只留与本主题强相关、对复现有用的坑与诊断 / 恢复办法；琐碎、一次性、跑题的不写。
- **少写"给 agent 自动执行的操作流程"**
  - 用什么 CLI、要不要 sudo、怎么备份回滚——操作者临场决定的事不进正文，reference 只描述**目标产物长什么样**。
  - **例外**：面向人的 GUI 点选 / 物理接触设备的步骤，只能人做、agent 不会自动跑，写具体反而有用（人照着做）。
- **不过度限制、少堆告诫**
  - 陈述事实与权衡（必要时给被否决的备选及代价），让读者自己判断，少用"绝不能 / 务必"；复杂链路优先用 GitHub 能渲染的图。
- **引用状态**
  - 同 skill 内引用（`references/`、`assets/`、`scripts/`）都用相对路径（如 `references/foo.md`），不写绝对或 `~/...`；且目标真实存在（grep 验证）。
  - **章节级锚点**：引用精确到文件内某章节时，别用标题文字自动派生的 slug（如 `#安装步骤`）——GitHub 从标题文字生成 slug，标题一改（哪怕只改几个字）slug 跟着变，链接**不报错、只是跳不到位**（打开文件但停在顶部，容易被忽略）。改用嵌在标题里、与标题文字脱钩的显式锚点，链接指向它：

    ```markdown
    ## <a id="install-steps"></a>安装步骤
    见 [安装步骤](references/foo.md#install-steps)
    ```

    之后标题怎么改写（"安装步骤"→"部署指南"），只要不动 `<a id="install-steps">` 那一行，链接照样生效——改标题不用同步改引用处；同一文件内部的目录 / 章节跳转用同一套机制。
    - id 用英文 kebab-case、和标题文字脱钩（别把中文标题转拼音当 id），免得改标题时被"顺手把 id 也改一致"的直觉带偏。
    - 已用 GitHub 官方 `POST /markdown` 渲染 API 实测：GitHub 给显式 `id` 统一加 `user-content-` 前缀防冲突，但 `#id` 链接由同一套机制自动解析到位（和标题自动锚点同一条路径），写时不用理会这个前缀。⚠️ 只验证过 GitHub 渲染；VS Code 预览等其他渲染器通常也认 HTML `id` 但未逐一验证，引用前自行确认目标渲染环境。
  - **跨 skill 不写任何形式的文件路径**——相对路径（`../<other-skill>/references/x.md`）、绝对路径、`~/...`、"迁移指引"链接（"内容已迁移到 [.../x.md](../.../x.md)"）全部禁止。只写 `<skill 名>` 加能力边界（例："见 `software` skill 的 GitHub Copilot CLI 章节"）。理由：被引 skill 一旦重构 reference 文件名或拆分合并，所有跨 skill 链接都断；只写 skill 名 + 主题名，读者用 grep / SKILL.md 自己定位，永不断链。**没有"看似对用户更友好就破例"的豁免**——别在审查时被"明示目标对读者更顺手"的直觉劝退。
- **引用做成可点击链接**
  - 凡在正文提到同 skill 的 reference 文件、文件内章节、或引用的外部文档 / 源码，都包成 Markdown 链接让读者和 agent 一点直达（`[章节名](references/foo.md#install-steps)`、`[官方文档](https://…)`），别把路径 / 章节 / 出处写成纯文本或行内代码（`` `references/foo.md` `` 渲染出来点不动），逼人手动 grep 去找。
  - 具体写法不在本条重抄：同 skill 相对路径 + 章节 `<a id>` 锚点见上条「引用状态」，外部链接锁版本见下条「引上游源码 / 文档锁到版本」——本条只把关**最终形态得是能点开的链接**别漏这一步。
  - **例外：跨 skill 引用不做链接**，只写 skill 名 + 能力边界（理由同「引用状态」里“跨 skill 不写任何形式的文件路径”）——别为“可点击”给跨 skill 硬塞一个迟早会断的路径链接。
- **每条说法有据、来源与置信度就近**
  - 自己实测的直接陈述；引官方 / 外部挂可点开的链接（锁版本，见下「引上游源码 / 文档锁到版本」）；拿不准标注不确定，别凭记忆编。
  - 每条来源引用、每处结论的置信度就近标在讲到的地方（如紧跟其后的 `>` 引文块），别攒到文末做"参考文献 / 置信度"附录。理由：读者读到某句当场能核出处、判可信；文末附录对不上正文哪一句、增删时又容易漏改，最后烂成没人维护的清单。
- **引上游源码 / 文档锁到版本，别指滚动 ref**
  - 引**第三方仓库源码**：链接锁到不可变 ref，别用 `main` / `master` / `HEAD` 这种滚动分支——分支会漂、行号更漂，链接不报错但跳到的是另一段代码。GitHub 文件页按 `y` 把 URL 重写成 commit-SHA permalink，shift 点选行段得 `#L120-L135` 行锚；**行号写进 URL 片段，别当纯文本注解堆正文**（正文注解点不过去、照样随版本漂）。

    ```
    github.com/OWNER/REPO/blob/v0.80.6/path/file.ts#L120-L135   # tag：可读、与正文实测版本对齐
    github.com/OWNER/REPO/blob/<sha>/path/file.ts#L120-L135     # SHA：要绝对不可变时
    ```

    - **tag 还是 SHA**：默认用 release **tag**——可读、和正文实测版本对得上、重新核验时全文替换一个字符串即可 bump；但 tag 理论上能被上游重打（git 不禁止），要绝对不可变或钉某历史态就用 **SHA**（不透明、但删 tag 也活）。两全就"链接文字写 tag、URL 指 SHA"（GitHub 按 `y` 给的永久链就是 SHA 形式）。
  - 引上游**在线文档**同理，别指滚动的 `latest` / `stable`：① 站点有版本化 URL（`/docs/v0.80/…`）就锁那个；② 只有滚动 `latest` 就改引**仓库里 docs 源码 `.md`、锁同一个 tag**（渲染站就是从这些 md 生成，内容一致、只是看 raw），或存 archive.org 快照按日期引。渲染站链接留作次要"顺手看"，**引用凭据用锁版本那个**。
- **标题命名**
  - 一句话判据：标题命名**这节是什么**（主题 / 对象 / 类别），不预告**这节得出什么**（结论 / 计数 / 实测数值 / 优劣判断）。
  - 计数 / 数据入题 → 去数字留类别：`钩子事件：33 个` ✗ → `钩子事件（通知 vs 可改写）` ✓；连"三种 / 两个"这类量词也算计数（`社区包（三种编排范式）` ✗ → `社区包（编排范式）` ✓）。
  - 结论入题 → 换成主题：`缓存命中：服务端自报说了算` ✗ → `缓存命中的判定` ✓。
  - 排名 / 优劣入题 → 换成客观属性：`方案 A —— 最简单` ✗ → `方案 A —— 单进程` ✓。
  - **具体 ≠ 违规**：具体信息若是**对象自身的身份**就留——`实测快照：某网关（2026-07）` ✓（端点名和日期是它的身份，不是它的结论）。
  - **多毛病叠加 → 属性全下放正文、标题只留对象名**：状态 / ★ / 排名 / 限定语别堆标题——`` `badlogic/pi-telegram`（🟧，~253★）——最简单 `` ✗ → `` `badlogic/pi-telegram` `` ✓（🟧、★、"最简单"改叙述进正文）。
  - **并列小节靠差别命名**：兄弟小节靠**客观属性 / 对象面向**（`多渠道`、`强隔离`）区分，不靠**排名**（`最简单`、`最推荐`）——差别化和"别塞判断"是同一条的正反面。
  - **有主题就别戴帽**：一节真有具体主题就直接用主题命名，别再罩 `TL;DR` / `结论先行` 这种"读法提示"帽子。（`速览` / `概述` / `小结` / `速查` 真的是概览 / 汇总 / 速查的那类小节，合法保留。）
  - **用词书面**：标题名词化、书面化，少用口语设问 / 俚语（"谁说了算""从哪来""发什么"）——`缓存命中的判定` 胜过 `缓存命中数从哪来`。
  - **预读可懂**：让还没读这节的人也能看懂，别用只有读完才懂的自造术语 / 比喻 / 内部代号（"地基""三个位置""commit 快照规律"）；要用专名就用领域公认词，不是现造的框架名。
  - **标题不编号，序号式交叉引用一并禁**：别给标题写序号（`## 1. 安装`、`### 2.1 …`），正文也别用 `§1.2`、"见第 3 节"这种序号交叉引用——章节一增删 / 重排，序号全体错位、得手工重编号；序号锚（`§2.1`）和标题 slug 一样脆（改了不报错、只跳错位）。内部互引只走 `<a id>` 显式锚点。（顺带：能力 / 主题命名的标题也比"第 N 节"更有信息量。）
  - 配套：改带显式锚点 `<a id>` 的标题时只改文字、**不动 `<a id>`**。
- **不硬编码仓库 clone 位置**
  - skill 正文、reference、README 里不要把 skills 仓库位置写死为 `~/skills`、`C:\Users\...\skills`、`/home/.../skills` 等具体路径；需要表达仓库根目录时用 `<repo>` 这类占位符，并说明由当前安装位置决定。
- **脚本运行与依赖声明**
  - 正文或 reference 里提到运行同 skill 自带 Python 脚本时，应要求使用 `uv`，脚本路径保持为当前 skill 根目录下的 `scripts/` 相对路径，不写绝对路径、`~/...`、上层跳转路径或绑定本机仓库位置的路径。
  - 脚本的 Python 版本与第三方依赖应放进 PEP 723 内联脚本元数据（inline script metadata），不要把安装命令或临时依赖细节堆进 skill 正文。
- **渐进式披露三层完整、分工清晰**
  - `frontmatter description` → `SKILL.md` → `references/*.md`
  - description：只写"何时触发 + 核心思路一句话"。
  - SKILL.md：短规则 + 各主题入口 + 子文档索引；不堆长流程与整段命令。短小高频的规则直接放 `SKILL.md`；长流程、低频细节、可独立维护的主题放 `references/`。
  - references/：单主题一文件，长流程 / 踩坑 / 模板。**单文件长度本身不是问题**——只要全篇围绕一个主题，几千行、几十 KB 的 reference 完全合规；不要因为文件"看起来大"就建议拆分，拆分依据永远是"出现了第二个独立主题"。
  - 常见病：SKILL.md 堆满命令（该下放）；references 存在但 SKILL.md 没索引（找不到入口）；description 太笼统或太具体。
  - 判定：SKILL.md 读完应当知道"能做什么、哪个 reference 讲什么"，**不应该读完就能完成具体任务**，那说明 references 层缺位。
  - 挪 / 拆内容时先确认新位置覆盖完整原文，再删旧正文；别留重复。
- **个人配置不入 skill 正文 / 可复现、不绑定本机**
  - 凭据 / 域名 / 服务器地址 / 主机名 / IP / 用户名 / 私有路径 / 个人样例文件名都不写进 skill 正文；隐去后用占位符（`<入口VPS>`、`<user>`、`<repo>`）。正文只写变量名、占位符和读取位置，真实值放 `~/.env` 或个人笔记。
  - 路径、目录名这类"换台机器就不同"的，讲清作用即可。
- **不绑定特定 AI 工具的具体工具名**
  - skill 正文不写 `AskUserQuestion`、`TodoWrite`、`WebFetch`、`Task` 这类特定宿主（Claude Code / Codex / Cursor / Trae 等）独有的工具名。
  - 改写成能力描述："向用户提问的工具"、"任务清单工具"、"抓网页的工具"，由模型按当前环境自己挑。
  - 只有当 skill 明确只服务单一宿主、且在 description 里讲清楚时才可以保留具体名字。
- **README 与 skill 实际状态同步**
  - README 表格条目的名称 / 来源 / 说明要和 skill 自身的 frontmatter `description` 口径一致。
  - 合并 / 拆分 / 重命名 / 删除 skill 后，README 不能留 stale 条目。
- **跨 skill / 对照上游的专项检查另有出处**
  - 嫁接 skill 的上游 LICENSE 存否、是否落后上游、`name` 全局唯一——这几项要把全仓摆一起或对照上游才做得出，只在审查时跑，见 [review.md](review.md)，不在本清单重复。
- **其他结构性检查**
  - frontmatter `name` 与目录名一致。
  - 重命名 skill 后，同步更新 frontmatter `name`、标题、描述，以及其他 skill 里指向它的纯文本提示。
  - 弃用段落删掉，别留历史遗迹。
  - 任何可疑处照实记下让用户决断。
