# 解决合并冲突

把两条分叉的 skill 文档分支合到一起（尤其双向分叉、两边各自重构了同一大文件、或术语 / 定义分歧）。核心思想：**合并不是机械删冲突标记，而是理解两边意图后，重建一份一致、不丢信息、无重复的知识**。冲突标记只圈出了"文本重叠"处，真正的活是判断与重构。

与 [refactor.md](refactor.md) 的单篇结构重排不同——这里要同时消化**两个来源**并调和它们；但一旦某个文件的合并演变成结构性大改，就回到 refactor.md 那套"先出大纲、批准后动手"。全程对照 [conventions.md](conventions.md)。

## 先定策略：merge 还是 rebase

解冲突之前先定用哪种合并方式，别默认下手。

- **merge**（生成一个合并提交）：适合**双向分叉、提交量大、要保留真实并行历史、且分支已推送**——冲突只在合并点**解一次**、不改写任何已有提交 SHA。代价是历史非线性（多一个合并节点）。
- **rebase**（把一侧提交逐条重放到另一侧之上）：适合**分叉小、未推送、想要线性历史**。代价：可能**跨多个提交反复解同一冲突**、且**改写全部被重放提交的 SHA**（已推送的分支会逼下游强推）。
- 判据：几十上百个提交的双向分叉、两边都已推送 → 默认 **merge**；少量本地未推提交、只想跟上游对齐 → 可 **rebase**。

## 动手前：勘定环境与无损预演

- **先勘定仓库真实状态**，尤其接手一个进行中的合并：核对当前分支头是否如交接所述、有没有并发会话在动同一仓库（提交历史 / reflog、文件改动时间、锁文件都是线索）。基于过时或想当然的状态假设动手，后面会连环出错。
- **动手前重新 `git fetch` 并复核领先 / 落后**：`git rev-list --left-right --count <upstream>...HEAD` 看两边各领先多少条。远端和本地都可能在你上次查看后又漂移（远端有人推新提交、本地有并发会话加 commit）——拿旧的 ahead/behind 数字开工会误判分叉规模与策略。
- **无损预演冲突清单**：用 `git merge-tree --write-tree <ours> <theirs>` 提前算出会冲突哪些文件（输出里的 `CONFLICT` 行即冲突文件清单）——它只写 git 对象库、**不碰工作区与索引**（不是字面"纯内存"，但对工作区零副作用），心里有数再动工。
- **别在损坏的输出上做决定**：命令输出若乱码 / 截断 / 花屏，重跑一次干净的再判断。

## 三方溯源、先看意图

这一步最容易被跳过、却最关键。

- 每处冲突都比 **base / 我方 / 对方** 三方，并**读双方的提交信息与 diff**，先讲清“两边各改了什么、为什么改”。（`git merge-base <ours> <theirs>` 定 base；`git show <base>:<file>` 看分叉起点原样、`git log <base>..<theirs> -- <file>` 读对方在这文件上的提交信息、`git show <sha> -- <file>` 读某条改动的 diff。）
- **别急着判某一侧"没意义 / 措辞变差"**：对方很可能是**刻意**换了另一套设计、定义或结构，不是退化。断定"劣化"之前先找到它的意图；拿不准就查一手来源或问用户，别凭印象否掉一侧。

## 冲突分类与对应手法

先给冲突归类，再套手法：

- **纯并集**（两边在同一处各加不同条目）→ 双方都留。
- **干净超集**（一侧内容完全覆盖另一侧）→ 取超集侧。
- **结构 / 语义分叉**（两边各自重构了同一大文件）→ 选**更全 / 更合规**的一版做底本，从另一侧 splice 进独有价值，去重。
- **术语 / 定义分叉** → 先查业界一手来源（可派 research 子代理系统检索、引用锁到版本，别凭记忆定谁对；但注意：项目内自定义的义、或两个上下文相关的义项，也可能都成立，未必有唯一“对”），定下后**全 skill 一致**落地：一处的用词改了，别处的措辞与交叉引用都要跟着改。

## 自动合并的静默重复（冲突标记之外）

- 行级自动合并**只在文本重叠处报冲突**。两边若在同一大文件的**不同位置**各加了语义相同 / 相关的内容，自动合并**不报冲突**，却会留下**重复段、错位顺序、被拆散的小节**——这些不在任何冲突标记里。
- 所以**删完所有冲突标记 ≠ 合并完成**：还要**通读整个自动合并结果的结构**（标题树、索引清单），把重复、错位、该并未并的段落当成结构缺陷一并修掉。索引层（SKILL.md）尤其容易出现"同一 reference 被两版各挂一个入口"的重复。

## splice 后的交叉引用修复

- 编号标题、章节序号、标题派生的 slug 锚点都很**脆**：一改就让指向它的引用**悄悄失效**（不报错、只跳错位）。这正是 conventions 坚持标题不编号、章节跳转走显式 `<a id>` 锚点的原因（见 [conventions.md](conventions.md)）。
- 从一侧 splice 过来的段落，其**内部引用往往沿用源文件的编号 / 锚点体系**，落进目标结构里就成了死链——splice 后逐条核对并改写。
- **重编号是脆的**：**正确的结构位置 + 修好锚点/引用优先**；在此前提下能**追加**而非插队重排就追加，把锚点失效面压到最小——但别为了保号把内容塞到不该在的位置。非重排不可时回到重构流程。

## reference 先于 SKILL.md

渐进式披露三层里，SKILL.md 是**索引 / 描述层**，内容跟着 reference 定稿走。**先定 reference，再让 SKILL.md 的描述与索引准确反映最终章节**；顺序反了会白改两遍。

## 大改走重构流程

结构性重排、两版融合这类大改，别直接动手：按 [refactor.md](refactor.md) **先分别提交「标题方案」和「内容迁移表」供审阅，两轮批准后再动**，让"丢信息 / 留重复"无处藏。

## 提交范围：隔离并发与脏改动

- 合并会把对方分支的**非冲突改动自动带进来**——这是合并语义的正常部分，该留。
- 但工作区可能还混着**并发会话未提交的脏文件、未跟踪文件**：那是别人的活，**绝不能顺手 stage 进本次合并提交**。动手前就分清"合并该带的"和"无关脏改动"。
- **要修的文件同时躺着别人的未暂存改动**时，别整文件重新 `add`（会把并发改动一起吞掉）。**优先 `git add -p`（hunk 级）/ `git add -e`（行级）做选择性暂存**，只挑本次该提交的改动，让并发脏改动原样留在工作区。只有当同一 hunk 里两拨改动交织、`-p` 也拆不开时，才动索引底层：`git hash-object -w <改好的文件>` 拿到 blob sha，再 `git update-index --cacheinfo 100644,<sha>,<路径>` 把这一版单独塞进暂存区、不碰工作区——这步绕过工作区，**务必先核对路径没写错、blob 就是你要的那版**，错了不易察觉。整文件级 / hunk 级 / 索引底层各手法的取舍见 `software` skill 的 Git CLI 精准操作章节。

## 验证与落地机制

- **解决即验**：确认无残留冲突标记（`grep -rnE '^(<<<<<<< |=======$|>>>>>>> )' <改动文件>` 应为空）；含大量链接的文件跑链接检查；**动过编号标题 / 锚点的**全量核对引用有没有断（把文件里的 `](#…)` 内链逐一对到标题 slug）。
- **区分"链接真断"与"检查器 / 环境的假阴性"**：链接检查失败不等于链接坏了。先用别的手段（直接请求 / 浏览器）实测链接是否真有效；若只是检查器的 TLS 栈 / 内置根证书 / 本机网络代理对**某个 host** 的假阴性，别为迁就工具删掉好内容或给全仓加忽略——按环境实情选**副作用最小**的放行方式。
- **落地手法**：安全网可能拦"取某一整侧"的破坏性命令（如 `git checkout --ours/--theirs`、`git checkout -- <file>`，怕丢未提交改动）；取整侧改用"把某个版本的文件内容直接写出来覆盖"（`git show <ref>:<file> > <file>`），局部则用编辑工具删标记。⚠️ **`git show > <file>` 会覆盖该文件工作区里的未提交改动**——只有先确认这个文件没有并发 / 无关脏改动时才安全；若它同时躺着别人的活，改走上面"提交范围：隔离并发与脏改动"那套只动暂存区的手段。取整侧后再做增补，末尾用 diff 只看自己的增补，便于自审与他人 review。
- **收尾**：全部解决并暂存后，状态应无 unmerged；**最终合并提交交用户确认**，提交信息**不带任何署名 / 追踪 trailer**。
