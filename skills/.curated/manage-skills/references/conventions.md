# skills 规范

本文件是写 / 改 / 审查 / 重构 skill 的共同准绳，也是这些规则的唯一出处。不应在别的 skill 或 AGENTS.md 等文件中重抄这些规则，如果非常需要这么做，就写 skill 名 + 文件名指过来。写作时照着要求列表来做；审查时逐文件、逐条核对，做跨 skill 的专项检查；重构单篇文档时，逐个对照要求，指出原文档的问题，提出改进方案。审查与重构的具体流程见 [review.md](review.md) 和 [refactor.md](refactor.md)。

- **像人类一样去说话**
  - 提到一个概念时，应理清其属于特定于本轮会话的、自创的"黑话"，还是领域中经常提及、通俗易懂的"常识"。对于黑话的情形，应当尽可能避免引入特殊的说法或概念，用更为明确的话来阐述；仅在需要大量提及自创黑话时，先介绍其定义，然后用它来阐述，注意保持全文名词含义的一致性。对于常识的情形，也应当通过引用的方式，给出其权威定义来源，避免产生歧义。
  - 总是先从较为上层的角度来讲整章或整节的逻辑。每个由标题划分的章节或小节，开头先简要说明本节要做什么、与上下文有什么关系，再进入具体细节；内容较多时，结尾概括本节的结果或下一步，不需要单独总结时也要自然收束，避免停在列表、命令或局部细节上。
  - 以上规则有利于对该领域不甚了解的用户快速、准确学习关键知识，过程中不与文档撰写者之间产生定义或理解上的偏差。
- **不说废话**
  - 不属于讲述主线的内容不要挤进正文：与当前说法直接相关的短补充放进 Markdown 引用块（`>`），形成独立主题的内容另设章节，其余不讲。
  - 反复表达同一个意思、没有带来额外信息量的话不讲。
  - 不滥用"不是...而是..."这类句式，能正向讲明白，就直接正向表述。
  - 以上规则能有效避免行文的拖沓和啰嗦，确保每一句话的存在都是有意义的。
- **简洁、准确地展示代码或配置**
  - 简洁指的是代码块只展示完成目标所需的关键代码、命令或配置，以及理解它们所需的最少上下文，不复制与目标无关的样板或过长的完整实现。未经用户允许，不应在 `scripts` 目录中新建文件再让正文引用。执行流程、条件分支、决策依据和方案取舍用文字讲清楚，不把这些信息藏进大段代码或命令；需要落实精确语法、接口或配置时，再用简短、可操作的代码块表达。
  - 准确指的是不应浮于大段的空讲，而可以用精确的、可操作的代码或命令解决一些地方词不达意的问题。
  - 以上规则不仅保障了文档结构的强逻辑性，还提高了文档描述的准确性，这既方便人阅读，又使其传达的操作等信息可以得到灵活而准确的实现。
- **具体、流程化地展示图形界面的操作流程**
  - 需要人物理接触设备或频繁且快速地做视觉反馈的任务，应该交给人来操作，此时应当提供清晰的操作流程，包括操作的预期结果、分支的选择等。
  - 让人程序化地做事情，使用这种伪代码的描述比纯自然语言描述更高效。
- **客观、完整地讲述内容**
  - 未经写 skill 用户允许，不得在文档中主动推荐方案，仅需完整陈述事实即可。由读 skill 的用户自行权衡利弊，做出选择。
- **自然穿插踩坑 / 排障相关内容**
  - 不在单独的章节中集中展现踩坑内容，而是在对应的讲述过程中写应该采用的正确做法。如果无法简洁地讲清楚问题所在，必要时可以用 Markdown 的引用块在段末详细说明。
  - 只留与讲述目标强相关、对复现有用的坑与诊断 / 恢复办法；过于琐碎的、一次性的、跑题的不写。
- **必要时澄清关键决策**
  - 在用户要求不甚明确时，使用 `grill-me` skill 向用户提问，问的问题应该把握主要逻辑和主要矛盾，不陷入过深。
  - 本规范和用户提出的各种要求，都不应该直接出现在写的 skill 中，也就是说，产物本身不应该包含生成或改造此产物过程中提出的要求。
- **完整、分工清晰地进行三层渐进式披露**
  - 在 skill 的设计中，存在三层的渐进式披露：`frontmatter description` → `SKILL.md` → `references/*.md`。渐进式披露的意思是，读一层会让 agent 知道何时需要读取下一层，而不是每次把三层全部读完。
  - description：写"做什么、何时触发 + 核心思路一句话"；保持 1–2 句，不逐项枚举章节、命令、实现细节或踩坑，且不超过 1024 个字符。
  - SKILL.md：短规则 + 各主题入口 + 子文档索引。
  - references/*.md：可独立维护的单一主题 + 丰富的内容；单文件涉及不同的独立主题时建议拆分，文件长度本身不是拆分理由。
- **完善内容呈现形式**
  - 需要对多个对象按同一组属性进行比较，或内容量大且结构重复时，优先使用表格提高信息密度。列所代表的比较维度应定义明确、边界清楚、彼此不重复；同一列的单位、状态和口径保持一致。简短的线性说明或结构差异很大的内容不要强行塞进表格。
  - 要呈现的内容量大时可以尝试使用 Mermaid 代码环境展示逻辑关系、流程图等。
  - 图片确实能够增强表达时，可以搜索有适当使用许可的网络图片，或使用当前环境可用的图片生成能力；注明来源或生成方式，并提供替代文本。
- **多任务用 subagent**
  - 多个相互独立、能够清楚划分上下文的子任务可以并行委派；单一连续问题不要为了并行而拆开。最终由主执行者统一术语、判断标准和结论。
- **引用与来源**
  - **补充说明放进引用块**：不属于正文主线、但与当前说法直接相关，仅用于补充来源、严谨性、限制条件或例外的信息，紧跟相关段落放进 Markdown 引用块（`>`）。读者理解和执行所必需的对象、动作、条件、结果与风险仍写在正文；较长或独立的补充内容移到单独章节或 reference。
  - **说法有据，来源与置信度就近**：实测结果说明实测条件；外部事实优先引用官方或一手来源；拿不准就标注不确定，不凭记忆补全。来源和置信度紧跟对应说法，不集中堆到文末。表格整表同源时在表格下统一列出；各行来源不同时增加来源列或脚注。
  - **引用做成可点击链接**：同 skill 的 reference、文件内章节和外部文档 / 源码都使用 Markdown 链接，不把路径或出处写成纯文本。同 skill 内使用相对路径并确认目标存在；跨 skill 不写路径、不链接内部文件，只写 skill 名和能力边界，避免对方重构后链接失效。
  - **章节引用使用稳定锚点**：不要引用随标题变化的自动 slug；在标题中添加与标题文字脱钩的显式 `<a id>`，链接指向该 id：

    ```markdown
    ## <a id="install-steps"></a>安装步骤
    见 [安装步骤](references/foo.md#install-steps)
    ```

    id 使用英文 kebab-case；修改标题文字时不改 id。同一文件内的目录和章节跳转也使用这种锚点。
  - **上游源码和文档锁定版本**：第三方源码链接使用 release tag 或 commit SHA，并把行号写进 URL（如 `#L120-L135`）；不要指向会变化的 `main`、`master` 或 `HEAD`。默认使用便于核对版本的 release tag，需要绝对不可变时使用 SHA。

    ```
    github.com/OWNER/REPO/blob/v0.80.6/path/file.ts#L120-L135
    github.com/OWNER/REPO/blob/<sha>/path/file.ts#L120-L135
    ```

    在线文档优先引用带版本号的 URL；站点只有滚动的 `latest` 或 `stable` 时，引用同版本仓库里的文档源码，或使用按日期保存的网页快照。滚动页面可以作为阅读入口，但不能作为固定引用凭据。
- **标题命名 / 文件名命名**
  - 一句话判据：标题命名**这节是什么**（主题 / 对象 / 类别），不预告**这节得出什么**（结论 / 计数 / 实测数值 / 优劣判断）。
  - 文件名沿用相同判据：命名文件所讲的对象或主题，不写结论、计数或排名；reference 文件名使用简洁、稳定的英文 kebab-case。
  - 计数 / 数据入题 → 去数字留类别：`钩子事件：33 个` ✗ → `钩子事件（通知 vs 可改写）` ✓；连"三种 / 两个"这类量词也算计数（`社区包（三种编排范式）` ✗ → `社区包（编排范式）` ✓）。
  - 结论入题 → 换成主题：`缓存命中：服务端自报说了算` ✗ → `缓存命中的判定` ✓。
  - 排名 / 优劣入题 → 换成客观属性：`方案 A —— 最简单` ✗ → `方案 A —— 单进程` ✓。
  - **具体 ≠ 违规**：具体信息若是**对象自身的身份**就留——`实测快照：某网关（2026-07）` ✓（端点名和日期是它的身份，不是它的结论）。
  - **多毛病叠加 → 属性全下放正文、标题只留对象名**：状态 / ★ / 排名 / 限定语别堆标题——`` `badlogic/pi-telegram`（🟧，~253★）——最简单 `` ✗ → `` `badlogic/pi-telegram` `` ✓（🟧、★、"最简单"改叙述进正文）。
  - **并列小节靠差别命名**：兄弟小节靠**客观属性 / 对象面向**（`多渠道`、`强隔离`）区分，不靠**排名**（`最简单`、`最推荐`）——差别化和"别塞判断"是同一条的正反面。
  - **有主题就别戴帽**：一节真有具体主题就直接用主题命名，别再罩 `TL;DR` / `结论先行` 这种"读法提示"帽子。（`速览` / `概述` / `小结` / `速查` 真的是概览 / 汇总 / 速查的那类小节，合法保留。）
  - **用词书面**：标题名词化、书面化，少用口语设问 / 俚语（"谁说了算""从哪来""发什么"）——`缓存命中的判定` 胜过 `缓存命中数从哪来`。
  - **预读可懂、对象具体**：标题应让还没读正文的人也能知道本节讲哪个具体设备、文件、操作或现象，以及关注它的哪一方面。别用只给抽象分类、不说实际对象的标题（`设备专属说明`、`恢复边界`、`板级功能`）；改为直接点明内容（`不同型号的首次安装方法`、`正式安装后的原厂恢复方法`、`指示灯和按键的作用`）。也别用只有读完才懂的自造术语 / 比喻 / 内部代号（"地基""三个位置""commit 快照规律"）；要用专名就用领域公认词，不是现造的框架名。
  - **标题不编号，序号式交叉引用一并禁**：别给标题写序号（`## 1. 安装`、`### 2.1 …`），正文也别用 `§1.2`、"见第 3 节"这种序号交叉引用——章节一增删 / 重排，序号全体错位、得手工重编号；序号锚（`§2.1`）和标题 slug 一样脆（改了不报错、只跳错位）。内部互引只走 `<a id>` 显式锚点。（顺带：能力 / 主题命名的标题也比"第 N 节"更有信息量。）
  - 配套：改带显式锚点 `<a id>` 的标题时只改文字、**不动 `<a id>`**。
- **不硬编码仓库 clone 位置**
  - skill 正文、reference、README 里不要把 skills 仓库位置写死为 `~/skills`、`C:\Users\...\skills`、`/home/.../skills` 等具体路径；需要表达仓库根目录时用 `<repo>` 这类占位符，并说明由当前安装位置决定。
- **脚本运行与依赖声明**
  - 正文或 reference 里提到运行同 skill 自带 Python 脚本时，应要求使用 `uv`，脚本路径保持为当前 skill 根目录下的 `scripts/` 相对路径，不写绝对路径、`~/...`、上层跳转路径或绑定本机仓库位置的路径。
  - 脚本的 Python 版本与第三方依赖应放进 PEP 723 内联脚本元数据（inline script metadata），不要把安装命令或临时依赖细节堆进 skill 正文。

- **个人配置不入 skill 正文 / 可复现、不绑定本机**
  - 凭据 / 域名 / 服务器地址 / 主机名 / IP / 用户名 / 私有路径 / 个人样例文件名都不写进 skill 正文；隐去后用占位符（`<入口VPS>`、`<user>`、`<repo>`）。正文只写变量名、占位符和读取位置，真实值放 `~/.env` 或个人笔记。
  - 路径、目录名这类"换台机器就不同"的，讲清作用即可。
- **不绑定特定 AI 工具的具体工具名**
  - skill 正文不写 `AskUserQuestion`、`TodoWrite`、`WebFetch`、`Task` 这类特定宿主（Claude Code / Codex / Cursor / Trae 等）独有的工具名。
  - 改写成能力描述："向用户提问的工具"、"任务清单工具"、"抓网页的工具"，由模型按当前环境自己挑。
  - 只有当 skill 明确只服务单一宿主、且在 description 里讲清楚时才可以保留具体名字。
- **README 与 skill 实际状态同步**
  - README 表格条目的名称 / 来源 / 说明要和 skill 自身的 frontmatter `description` 口径一致。
  - 合并 / 拆分 / 重命名 / 删除 skill 后，README 不能留 stale 条目。
- **跨 skill / 对照上游的专项检查另有出处**
  - 嫁接 skill 的上游 LICENSE 存否、是否落后上游、`name` 全局唯一——这几项要把全仓摆一起或对照上游才做得出，只在审查时跑，见 [review.md](review.md)，不在本清单重复。
- **其他结构性检查**
  - frontmatter `name` 与目录名一致。
  - 重命名 skill 后，同步更新 frontmatter `name`、标题、描述，以及其他 skill 里指向它的纯文本提示。
  - 弃用段落删掉，别留历史遗迹。
  - 任何可疑处照实记下让用户决断。
