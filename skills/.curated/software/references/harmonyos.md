# HarmonyOS / HiShell 开发环境笔记

HiShell 中的命令行程序运行在终端应用的环境里。理解这个环境，需要分清应用与进程身份、路径映射、文件所有权和文件系统能力，再选择数据目录并验证程序的实际行为。工具安装与编译成功，只覆盖其中一部分。

> 来源与范围：目录、工具链、文件系统能力和性能来自用户提供的 2026-09-08 HiShell 会话摘录及带原始输出的性能报告；应用包名与配置属主问题来自用户后续补充的进程观察和排障记录。本文整理这些历史观察，并用一手文档解释机制，没有重新连接设备或重跑测试。具体版本、包名和能力不能推广为所有鸿蒙设备的共同属性。

## 应用身份与目录空间

应用包名标识软件，进程号描述某次运行，沙箱路径决定该进程看见哪一份数据。这些对象相互关联，但不能用其中一个替代另一个。

### <a id="bundle-identification"></a>应用标识与进程归属

Bundle ID（应用包名，对应应用配置的 `bundleName`）标识整个应用。HAP（Harmony Ability Package）是应用的模块安装包，一个应用可以包含多个 HAP；`entry` 是模块名称。`haps/entry/` 是按模块组织的数据目录，不是 `.hap` 安装包本身。

> 应用、模块及 `bundleName` 的关系见 [Stage 模型应用程序包结构](https://github.com/openharmony/docs/blob/c8e3168b26385fc0ccbce4bde4fec14e3af1936b/zh-cn/application-dev/quick-start/application-package-structure-stage.md)。

在具备相应进程可见权限的环境中，可以列出进程并还原父子关系：

```sh
ps -eo pid,ppid,comm,args
```

`PID` 是进程号，`PPID` 是父进程号，`COMM` 是进程名，`ARGS` 是命令行及参数。从目标进程的 `PPID` 找到对应的父进程 `PID`，逐级向上核对。用户提供的终端观察可概括为：

```text
com.huawei.hmos.hishell
└── zsh
    └── 命令行程序
```

当时的 shell 由名为 `com.huawei.hmos.hishell` 的进程启动，因此将终端应用识别为该包名。进程号会随运行变化，查询时使用当次输出；原记录的识别依据是进程链，`hdc` 查询没有提供这个结果。

查询其他运行中的应用仍可使用同一命令，再按关键词筛选。例如微信：

```sh
ps -eo pid,ppid,comm,args | rg '[w]echat'
```

`rg` 是文本搜索工具；`[w]echat` 匹配 `wechat`，同时避免匹配参数中带有该正则表达式的筛选命令本身。未找到时可先启动目标应用再查询，但权限、进程名和输出截断仍可能影响结果。

**进程列表只覆盖当前可见的运行进程，不是已安装应用清单。** `COMM`、`ARGS` 不保证直接显示包名，关键词也可能命中辅助进程或无关参数。需要完整安装列表或权威包身份时，使用具备相应权限的包管理查询或安装清单；不能凭没有匹配到进程就断言应用未安装。

| 应用 | 观察到的 Bundle ID |
| --- | --- |
| 终端（HiShell） | `com.huawei.hmos.hishell` |
| 微信 | `com.tencent.wechat.pc` |
| QQ | `com.tencent.harmonyqq` |
| WPS Office | `cn.wps.office.hap` |
| 华为浏览器 | `com.huawei.hmos.browser` |
| 文件管理 | `com.huawei.hmos.files` |
| 小艺输入法 | `com.huawei.hmos.inputmethod` |
| ClashBox | `org.xbgroup.clashbox` |

> 整表来自用户补充的 HiShell 会话摘录：终端通过父进程链识别，其余应用通过运行进程识别。没有应用版本、安装清单或签名核验信息，不能当作跨版本、跨设备、跨发行渠道的官方包名目录。

### 用户文件区与应用私有目录

用户文件区承载用户管理的项目、文档和软件；应用私有目录承载当前应用自己的数据。记录中的目录视图如下：

```text
/storage/Users/currentUser/          用户文件区：项目、文档、下载及 .harmonybrew 等
/data/storage/el2/base/             当前应用的私有数据视图
├── files/                         应用级持久文件
├── cache/                         应用级缓存
├── preferences/                   应用级设置数据
└── haps/
    └── entry/                     entry 模块的数据
        ├── files/                 模块级持久文件
        ├── cache/                 模块级缓存
        ├── preferences/           模块级设置数据
        └── temp/                  模块级临时文件
/tmp/                              该次环境中为只读的 erofs 挂载
```

不同应用可以看到相同的 `/data/storage/el2/base/...` 路径，但它们映射到各自的数据。HiShell 启动的子进程使用该终端应用的环境；换成其他应用或 `hdc shell`，看到的路径和权限可能不同。用户文件区的跨应用访问也受系统权限控制，不能理解成任意应用都能无条件读写。

应用开发通过上下文对象 `Context` 获取路径：`ApplicationContext` 获取应用级目录，`UIAbilityContext` 等获取 HAP 级目录；分别使用 `filesDir`、`cacheDir`、`tempDir` 等属性。上面的绝对路径用于描述历史 HiShell 环境，不应硬编码为跨设备接口。

> 目录模型与路径隔离见 OpenHarmony [应用沙箱目录](https://github.com/openharmony/docs/blob/c8e3168b26385fc0ccbce4bde4fec14e3af1936b/zh-cn/application-dev/file-management/app-sandbox-directory.md)。该文包含应用级 `base/temp`，但 `/data/storage/el2/base/temp` 在所记录的设备检查中不存在；这不是所有鸿蒙设备都没有应用级临时目录的证明。

## 文件所有权与权限语义

文件能被读取，只说明当前访问被允许；程序还可能自行检查文件是否由可信身份持有、是否能被其他人修改。权限排障需要同时看进程身份、文件元数据和程序的安全检查规则。

### 进程身份、文件属主与权限位

下面这些字段分别回答不同问题，不能仅凭其中一项正常就排除权限故障。

| 对象 | 含义 | 核对方式或注意事项 |
| --- | --- | --- |
| 本地进程 UID | 运行命令的本地用户身份 | `id -u` 查看有效 UID，`id -ru` 查看真实 UID；普通进程通常相同，提权或切换身份时需区分 |
| 文件属主 UID | 文件元数据中的所有者 | 查看实际目标文件的数字 UID，与程序要求的身份比较 |
| 文件权限位 | 属主、组和其他用户的读写执行位 | `0600` 表示权限位仅授予属主读写；它不会改变文件归谁所有，也不是 ACL（访问控制列表）、沙箱规则和程序安全检查的全部 |
| 路径与父目录 | 文件如何被找到、路径能否被替换 | 软链接本身、链接目标和父目录都可能需要检查 |
| 远程登录用户 | 客户端希望登录到服务器的账户 | 如配置中的 `User <remote-user>`；与本地配置文件属主是两回事 |

以用户补充的配置读取故障为例，`~/.ssh/config` 已经是 `0600`，但文件属主 UID 与 HiShell 中运行客户端的 UID 不一致，默认读取时报 `Bad owner or permissions`。该次直接原因是**属主不符合客户端检查要求**，不是配置语法，也不是缺少一次 `chmod 600`。

> 该结论来自用户提供的排障记录，没有在本文整理时重测。作为机制对照，OpenSSH 9.7p1 的 [配置文件安全检查](https://github.com/openssh/openssh-portable/blob/V_9_7_P1/readconf.c#L2460-L2470) 在启用检查时要求文件属主为 root 或当前真实 UID，并且组、其他用户不可写；它在打开文件后检查实际文件描述符。这个上游版本用于解释检查逻辑，不代表已经确认 HiShell 安装的 OpenSSH 版本或全部补丁。

查看元数据时，既要知道原路径是不是软链接，也要查看它最终指向的文件。以下为 GNU `stat` 语法：

```sh
id -ru
id -u
ls -ldn "$HOME/.ssh" "$HOME/.ssh/config"
stat -L -c 'uid=%u gid=%g mode=%a path=%n' "$HOME/.ssh/config"
```

`stat -L` 跟随软链接；只看链接自身的模式或只运行 `chmod`，无法证明目标文件符合程序要求。是否需要检查真实 UID、有效 UID、父目录或链接本身，由具体程序决定。

**数字身份与用户名查询。** 通常用 `whoami` 或 `id -un` 查询当前有效 UID 对应的用户名；`logname` 查询登录会话的登录名，含义不同。用户补充的 HiShell 观察中，前两个命令都无法把当前 UID 转成用户名，`logname` 则返回“没有登录名”。这说明这些查询在当时进程环境中不可用，不能推出进程没有 UID、没有文件访问权限或整个系统没有用户。

```sh
whoami
id -un
logname
```

**程序采用的远程用户名。** 本地用户名查询失败时，仍可单独查看 SSH 最终计算出的 `user` 配置字段。下面在 zsh/bash 的子 shell 中查看没有用户及系统配置覆盖时的默认值，不发起 SSH 连接：

```sh
(set -o pipefail; ssh -G -F /dev/null example.invalid | awk '$1 == "user" {print $2}')
```

`-G` 输出生效配置后退出；`-F /dev/null` 使用空配置并排除常规用户、系统配置文件的影响。这里保留标准错误，并用 `pipefail` 让前面的 SSH 失败不被 `awk` 的成功掩盖。**这条命令隔离的是默认用户名，不用于验证 `~/.ssh/config` 已修复。** 要看某个实际别名所采用的远程用户名，应使用不带 `-F` 的 `ssh -G '<主机别名>'`。

> 用户记录中，隔离配置后的查询输出为 `user`，而 `whoami`、`id -un` 无法返回用户名；`user` 因此只记为该客户端当时采用的默认远程用户名，不能认定为鸿蒙系统登录名。OpenSSH 9.7p1 上游先用 [`getpwuid(getuid())`](https://github.com/openssh/openssh-portable/blob/V_9_7_P1/ssh.c#L713-L720) 查询本地真实 UID，未指定远程用户时再[使用查询所得名称](https://github.com/openssh/openssh-portable/blob/V_9_7_P1/ssh.c#L1291-L1296)。各命令的实际身份语境、移植补丁和运行库实现尚未交叉核验，兼容处理只是待验证的解释；本文没有定位该差异的具体实现。配置读取入口和 `-F` 的分支见[同版源码](https://github.com/openssh/openssh-portable/blob/V_9_7_P1/ssh.c#L560-L591)。

### 文件系统能力差异

历史记录将用户目录标识为 `hmdfs`、应用私有测试目录标识为 `hmfs`。它们是访问路径上的文件系统标识，不表示一定处于两块不同的物理磁盘。

| 操作 | 用户目录 `hmdfs` | 应用私有目录 `hmfs` |
| --- | --- | --- |
| 普通文件读写、同目录替换、软链接 | 通过 | 通过 |
| 创建 Unix 套接字（本机进程通信端点） | `EPERM`，操作不允许 | 通过 |
| 创建 FIFO 具名管道 | `EPERM` | 通过 |
| 创建硬链接（为同一文件增加目录项） | `EPERM` | `EACCES`，访问被拒绝 |
| 早期探测文件执行 `chmod 0600` | 返回成功，读回仍为 `0660` | 正确变为 `0600` |
| 跨进程 `flock` 文件锁、`mmap` 内存映射文件写回 | 通过 | 通过 |
| `user.*` 扩展属性、inotify 文件创建通知 | 通过 | 通过 |
| fio `direct=1` 直接 I/O 探测 | `EINVAL`（22），明确报告不支持 `O_DIRECT` | 通过 |

> 除 fio 一行外，表格来自早期文件系统补测的会话摘录，主要使用 Python 与部分 `ctypes` 调用；fio 一行有用户提供的性能测试原始输出。硬链接失败的具体原因尚未定位。表格只描述所测文件和调用条件，不是完整 POSIX（Unix 风格接口标准）符合性测试。

早期探测中“权限位没有按请求改变”和后续配置案例中“权限确为 `0600`，但属主不匹配”是**两种不同观察**。不能用前者覆盖后者，也不能推断用户文件区的每个文件都固定为同一个模式。需要检查的是当前文件的真实状态，而不是套用上一次的报错结论。

## 数据存放与程序适配

目录选择同时取决于数据的生命周期和程序需要的文件语义。遇到环境差异时，可以分别调整实际存放位置和程序查找路径，而不把所有问题都归为“权限不够”。

### 持久数据与运行时文件

需要长期保留的配置与可重新创建的通信文件，应按用途区分存放。

| 数据用途 | 对应位置 | 生命周期与约束 |
| --- | --- | --- |
| 用户管理的项目、文档和成果 | 用户文件区 | 用户自行管理与备份；特定 Unix 文件语义仍需验证 |
| 当前应用需要保留的配置 | 应用或模块 `files` | 持久不等于卸载后保留；应用卸载会清理私有数据，HAP 级数据也随相应 HAP 卸载清理 |
| 可重新生成的缓存 | `cache` | 可能被系统或用户清理，使用时检查是否存在 |
| 运行期间的临时文件、通信端点 | `temp` | 使用可丢弃的数据，不存放项目或配置的唯一副本 |

> OpenHarmony [目录属性与生命周期](https://github.com/openharmony/docs/blob/c8e3168b26385fc0ccbce4bde4fec14e3af1936b/zh-cn/application-dev/file-management/app-sandbox-directory.md) 将 `temp` 定义为运行期间使用、应用退出后清理的目录；不要依赖它跨应用生命周期保留。

所记录环境可用的模块临时目录为 `/data/storage/el2/base/haps/entry/temp`，末尾是 **`temp`**，不是 `tmp`。根目录 `/tmp` 当时只读，不能创建临时文件。

`TMPDIR` 是告诉程序“把临时文件放在哪里”的环境变量，不改变 `/tmp` 的挂载状态。遵循它的程序会使用指定目录，写死 `/tmp` 的程序仍可能失败。历史目录检查时命令进程的 `TMPDIR` 指向用户目录，因此变量存在也不能替代对值和目录能力的检查。

| 程序示例 | 依赖的能力 | 历史记录中的适配方式 |
| --- | --- | --- |
| 并行构建工具 Make | FIFO jobserver，用具名管道协调并行任务 | 为命令设置 `TMPDIR`，使用模块 `temp/mk`；默认 FIFO 后续验证可用，并非必须改成匿名管道 |
| 终端复用工具 Zellij | Unix 套接字 | 为命令设置 `TMPDIR`，使用模块 `temp/zj`；对应鸿蒙 ARM64 包的双窗格与退出验证通过 |
| 远程连接客户端 SSH | 配置文件的属主与权限检查 | 将配置迁入应用级 `files`，用软链接保留默认入口；具体迁移和验证见下文 |

前两个例子在原会话中通过 shell 包装函数设置命令专用环境；相同思路的一次性调用如下，不会全局更改其他程序的临时目录：

```sh
app_temp=/data/storage/el2/base/haps/entry/temp
mkdir -p "$app_temp/mk" "$app_temp/zj"
TMPDIR="$app_temp/mk" command make -j4
TMPDIR="$app_temp/zj" command zellij
```

`mk`、`zj` 是自建子目录，系统提供的是父目录 `temp`。子目录可能被清理，使用前需保证存在；这些测试也不代表相关软件的全部功能都已验证。

### 配置迁移与原路径保留

当默认文件位置的属主或权限语义不符合程序要求，而应用私有持久目录符合时，可以把**实际文件**与**查找入口**分开处理。软链接保留程序原有的路径约定，但安全检查是否接受该链接仍需逐个程序验证。

用户提供的配置修复案例形成了如下关系：

```text
~/.ssh/config
    → /data/storage/el2/base/files/ssh/config
```

这次修复迁移的是配置文件，不是整个 `.ssh` 目录。记录说明原文件已备份；目标文件由 HiShell 对应身份持有、模式为 `0600`，默认入口改为指向它的软链接，新启动的 zsh 中读取默认配置通过。

可复用的迁移步骤是：

1. 核对当前程序身份、原文件的属主和权限、原路径是否已经是链接，并备份原文件。
2. 在当前应用的持久 `files` 目录中准备目标文件，检查内容一致性、属主、权限和父目录访问控制。单纯移动文件或保留原元数据的复制不保证改变属主，不能只检查目的路径。
3. 确认目标正确后，让原路径指向目标；保留备份和恢复路径，不盲目覆盖已有链接或其他配置。
4. 从实际使用环境按默认入口启动程序，核对链接目标和程序自身的安全检查，再验证后续业务阶段。

软链接只解决路径兼容，不会消除原路径父目录可被替换的风险，也不能绕过所有程序对链接的限制。敏感配置还要核对相关目录的访问控制。应用卸载会影响私有目标文件；如果需要长期保留，应另有备份。

> 该案例没有验证私钥、`known_hosts` 或其他配置文件都已迁移且可用。对这套客户端配置，新的普通 `ssh` 进程会重新读取默认文件，因此修复后不需要长期追加 `-F`，也不依赖重载终端；这与修改 shell 的 `PATH` 或启动文件何时生效是不同问题。

### 分层验证与故障归因

修复一个阶段后，要报告实际到达的阶段。配置可以解析、程序能启动、网络可达和认证成功，各自验证的是不同能力。

| 验证层次 | 需要核对的现象 | 不能据此推断的结果 |
| --- | --- | --- |
| 文件元数据与默认入口 | 属主、权限、链接目标符合要求；按默认路径读取不再报错 | 密钥文件、网络和远端账户均正常 |
| 配置解析 | `ssh -G '<主机别名>'` 展示预期生效值；命令不带替代配置的 `-F` | 已建立连接或完成登录；仅用显式 `-F` 测试也不能证明原默认入口已修复 |
| 网络连接 | TCP 连接建立 | 协议握手、服务器身份校验或用户认证完成 |
| 协议与主机身份 | 进入握手、密钥交换或首次主机密钥确认 | 已通过用户认证；首次确认仍需核对可信来源的指纹 |
| 用户认证与业务操作 | 真正完成登录，并执行预期操作 | 未测试功能或后续连接始终可用 |
| 其他程序的业务验证 | 检查标准错误、实际资源与功能结果 | 仅退出码为 0 不代表没有降级或警告 |

**案例中的实际边界**：配置迁移后，在新启动的 zsh 中测试两个目标；一个已建立连接并进入首次主机密钥确认，尚未登录；另一个建立 TCP 连接后在握手阶段被对端关闭，也未登录。后者需继续排查对端服务或网络，不能再归因于已消失的本地配置属主错误。远程 `User` 设置不会修复本地文件所有权。

早期并行构建也出现过“退出码为 0，但仍有 FIFO 创建警告”，之后才在应用私有临时目录中验证默认 FIFO 工作正常。两类案例共同说明：验收应覆盖实际调用路径和预期功能，不能只停在解析或退出码。

> 以上连接状态来自用户提供的后续排障记录，并非本文整理时新发起的连接。通用 SSH 配置、主机身份校验、认证和服务端排查见 [SSH 笔记](ssh.md)，此处只保留鸿蒙文件环境下的案例与验证边界。

## 环境能力与性能记录

### 开发工具与功能验证

**工具分发与平台适配。** Harmonybrew 是社区维护的 Homebrew 鸿蒙适配项目；命令仍是 `brew`。Formula 是软件包的构建配方，Bottle 是预先编译好的软件包。它负责工具与依赖的获取、构建和安装，不会把应用沙箱变成普通 GNU/Linux 环境，也不会让同为 ARM64 的 Linux/macOS 二进制自动兼容鸿蒙。

历史环境的安装前缀为 `/storage/Users/currentUser/.harmonybrew`，包管理器仓库位于其下的 `Homebrew`；缓存则由 `${XDG_CACHE_HOME:-${HOME}/.cache}/Homebrew` 等独立位置承载，不能笼统认为所有数据都在安装前缀内。项目文档说明，用户文件区的位置兼顾鸿蒙 PC 中的可写性与跨应用共享；这种共享安装位置与每个应用自己的持久配置、运行时文件位置是不同层次。软件装在用户文件区，不意味着它运行时的所有数据也都应放在那里。

> 安装前缀、仓库与缓存布局见 [Harmonybrew 安装脚本](https://atomgit.com/Harmonybrew/install/blob/cd8a18e78b5701d6898e56ca76307fe03368f67c/install.sh)。项目定位、路径选择和平台适配的阅读入口：[维护者 FAQ](https://raw.gitcode.com/Harmonybrew/docs/raw/main/zh-CN/user/FAQ.md)、[社区说明](https://raw.gitcode.com/Harmonybrew/docs/raw/main/zh-CN/community.md)。后两者为滚动文档；维护者明确项目由社区独立发起，与华为和 OpenHarmony 社区没有隶属关系。

**平台软件包与版本边界。** 项目沿用上游配方机制，并针对 OHOS 的工具链、系统 musl 运行库和代码签名要求进行适配；不同包的具体编译器可以不同，配方能复用不表示普通 macOS/Linux Bottle 可以直接互换。维护者当前 FAQ 将鸿蒙 PC 列为次级支持平台，不做强制自动化测试或人工回归，并说明每包提供一个向新系统滚动的 `ohos` Bottle，不保证旧系统兼容。这些是所查滚动文档的政策，不用于倒推历史实测；升级后仍需验证实际功能。

**本地工具来源核对。** `brew --prefix` 查看安装前缀，`brew config` 查看包管理器报告的运行环境，`brew list --versions` 查看已安装版本，`brew info <包名>` 查看配方信息。调用到哪个二进制，还要看 shell 的命令解析：

```sh
brew --prefix
brew --prefix --installed ohos-sdk
brew config
brew list --versions
brew info devel-base ohos-sdk
type -a brew cc gcc clang make
clang --version
```

`brew --prefix ohos-sdk` 可以输出预期的包路径，并不一定证明已安装；`--installed` 要求该包已经安装。定位 SDK 时结合这个查询和实际文件，避免把某个 `Cellar/<包>/<版本>` 路径写死。

> 参数行为参考 [项目代码镜像中的前缀查询实现](https://github.com/HarmonybrewGlobal/brew/blob/c2dfc6bb47f8f4a07bcad775c48ec645e05d39f8/Library/Homebrew/cmd/--prefix.rb)。该链接是代码快照，不代表当前 AtomGit 分支或设备上的安装版本；具体可用参数仍以本机 `brew help --prefix` 为准。

不同 shell 可能读取不同启动文件，GUI 应用也未必继承交互 shell 的 `PATH`。安装后仍找不到命令或调用旧版本时，区分环境初始化、命令缓存和程序本身错误；不能把“已安装”当作“当前进程一定会调用它”。需要使用 `brew shellenv` 时，先查看它的输出，再按实际 shell 的启动方式配置。

### 短时性能快照

2026-09-08 17:58–18:04（Asia/Shanghai），所测机器标识为 **HUAWEI KirinX90A**，系统报告 **HongMeng Kernel 1.12.0**，16 个可见逻辑 CPU，进程允许使用 CPU 0–15；内存约 **23.30 GiB**，测试开始时可用约 **3.78 GiB**。使用 CoreMark 1.0、STREAM 5.10、fio 3.41，共 36 次正式测量，各项目取三轮中位数，另有 4 次 CoreMark 验证运行。

**CPU 与内存。** CoreMark 使用 Clang `-O3`、POSIX 适配代码和 pthread，每个上下文约 2 KB 工作集，未启用基于运行反馈的优化（PGO）或链接时优化（LTO）；正式测量及验证均超过 10 秒，标准性能种子与验证种子的循环冗余校验（CRC）通过。STREAM 使用 `-O3 -fopenmp`，每个数组 160 MB，三个数组共 480 MB，每轮各内核运行 20 次，数值校验通过。

| 线程数 | CoreMark 吞吐约值（iterations/s） | 相对单线程 | STREAM Triad 约值（GB/s） |
| --- | ---: | ---: | ---: |
| 1 | 16,985 | 1.00× | 35.25 |
| 4 | 62,145 | 3.66× | 38.97 |
| 8 | 97,993 | 5.77× | 36.38 |
| 16 | 141,174 | 8.31× | 37.37 |

> 来源：用户提供的性能报告与原始输出。CoreMark 列是总吞吐，不是每核分数；16 线程范围约 13.87 万–16.71 万，最大值比最小值高约 20.4%。STREAM 每轮排除首个内核迭代后报告最佳带宽，表中再取三轮报告值的中位数，不是全部迭代的平均带宽。末级缓存容量不可读取，未独立核验数组与缓存容量比例，不能视作已获官方收录的 STREAM 成绩。

**文件 I/O。** fio 在应用私有 `temp` 下新建测试文件，使用 `psync` 同步引擎、单任务、队列深度 1、`direct=1`，不访问裸磁盘。每轮顺序写入 1 GiB；顺序读和随机读写每轮运行 8 秒，写任务设置 `end_fsync=1`，所有正式任务 `error=0`。

| 项目 | 三轮中位数约值 |
| --- | ---: |
| 1 MiB 顺序读 | 1.56 GB/s |
| 1 MiB 顺序写 | 818 MB/s |
| 4 KiB 随机读 | 16,043 IOPS（约 65.7 MB/s） |
| 4 KiB 随机写 | 29,472 IOPS（约 120.7 MB/s） |

> MB/s、GB/s 使用十进制；IOPS 是每秒 I/O 操作数。用户目录拒绝 `O_DIRECT`，没有用其缓存读取速度冒充存储成绩。fio 构建关闭自动检测出的 `CONFIG_HAS_BLKZONED`，因为 OHOS SDK 缺少 `FALLOC_FL_ZERO_RANGE`；报告说明测试引擎源码未修改。

直接 I/O 不会排除设备内部缓存，结束时请求 `fsync` 不等于每次写入都测了断电持久化延迟；未测高队列深度、写满缓存后的持续写入或文件数据校验，不能用 `error=0` 替代内容完整性验证。

**测试条件与解释边界。** 开始前 1/5/15 分钟负载约为 23.10 / 24.50 / 23.87，其他应用未关闭；未固定 CPU 亲和性、频率或电源模式，温度不可读取。多线程计算吞吐有明显收益，STREAM Triad 在这组测试中四线程最高，继续加线程没有提高该项带宽；这些结果不能确定波动原因、机器极限、持续散热能力或对应哪档桌面处理器。
