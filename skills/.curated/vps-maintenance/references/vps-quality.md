# 质量检测

## 带宽测试 (iperf3)

目标机器上先启动服务端：

```bash
iperf3 -s
```

客户端测试：

```bash
iperf3 -c <目标IP>       # 测试上传
iperf3 -c <目标IP> -R    # 测试下载
iperf3 -c <目标IP> -P 4  # 并行流
```

## 延迟测试 (mtr)

```bash
sudo mtr -r -c 10 <目标IP> # 测试 10 次延迟
```

### 公网带宽限速丢包

2026-04 在标称 200 Mbit/s 的大陆 ECS 上用 iperf3 实测。阿里云超限直接丢包，不整形，所以裸跑能看到 TCP 一直在重传。

iperf3 用 `-b` 指定发送速率就能客户端限速：

```bash
iperf3 -c <目标IP> -b 160M      # 上行压到 160 Mbit/s
iperf3 -c <目标IP> -b 160M -R   # 下行压到 160 Mbit/s
```

实测数据（10 秒）：

| 方向 | 客户端限速 | 收到/发出 | 重传次数 |
|------|------------|-----------|----------|
| 上行 | 不限 | 238 / 261 ≈ 91% | 9 |
| 上行 | 160M（cap 的 80%） | 191 / 191 = 100% | **0** |
| 下行 | 不限 | 271 / 273 ≈ 99% | **14366** |
| 下行 | 160M（cap 的 80%） | 191 / 192 ≈ 100% | 38 |

几个点：

- **客户端限到 cap 的 80% 几乎就没丢包了**，收/发比贴着 1。
- 下行不限速时重传非常夸张（14366 次），因为服务器那边发得猛，更容易撞限速线。上行不限速只有 9 次，但吞吐直接掉到 91%。
- 90%（180 Mbit/s）也比不限强，但还有零星重传。想干净留 20% 余量最稳。

结论：跑延迟/丢包敏感的业务（实时音视频、游戏等），直接在客户端压到 cap 的 80%。

#### IP 类型判定随时间漂移（家宽 → 机房）

产品标称「双ISP 家宽住宅原生 IP」，但 ping0 的「IP 类型」判定**会随时间变**——同一个 IP 当时判「家宽」，过阵子重新测又变回「IDC机房 IP」，不是换到不同 IP 才不同：

- **2026-03-26（开通次日）**：初始 IP 被判 `IDC机房 IP`（风控 14% 极度纯净、原生 IP，大模型检测「家宽概率 16%」）。开工单反馈后客服（James Hills）手动换了一次 IP，约 10 分钟后复测变 `家宽`、风控更低。**但这个换来判家宽的 IP，后来再测也漂回了 `IDC机房 IP`**（分数仍还可以）。
- **2026-06**：被墙后付费换的新 IP（换 IP 经过见下「被墙与换 IP」）同样判 `IDC机房 IP`（风控 17% 纯净、原生 IP、共享 1-10）。

所以开工单换 IP 换出「家宽」只是**一时**的，别指望它稳定保持家宽；不过风控分一直还行、原生 IP 也在，日常用不受影响。
