# Reversing

静态逆向一个已发行的移动应用：**能读到什么、读到的东西怎么证明、结论怎么汇报**。不涉及动态调试与运行时 hook。

## 主题边界

- [APK 与 native 库的静态逆向](references/apk.md)：跨应用通用方法。解包分层、资产加解密、缺成套工具时读 native 库、从界面文案反查代码、数值规则表的语义还原、失效在线服务的本地替代、改包后的验证。
- [鸿蒙与 ANCO 容器](references/harmonyos.md)：平台侧实测。ANCO（鸿蒙里跑 Android 应用的容器）数据边界、HDC 权限墙、宿主备份到底覆盖什么、HMOSBackup 6.1 `encryptionType=2` 的解密链、迁移路径的可行域。
- [爱养成系列](references/aiyangcheng.md)：单个应用族的完整还原实例，并规定了结局达成条件的汇报格式——用户问"某结局怎么达成"时按 [结局达成条件的汇报格式](references/aiyangcheng.md#report-format) 回答。

## 通用判断

**先查符号表再动手。** 没 strip 的 native 库里，导出符号的类名和方法名就是作者写的目录；按业务名词过滤符号表，通常比在汇编里盲扫省事得多。引擎类应用（Cocos2d-x、Unity 等）的核心规则常落在 native 层而不是 Dex 层，但这只是常见形态、不是定律——两层都扫一遍再判断。

**"界面没显示"要读渲染函数才能定性。** 已实测到的成因至少有两种：该字段的渲染分支根本不存在，或有硬编码黑名单专门屏蔽某几条。数据表里两者长得一模一样，光看表分不出来。不排除还有别的成因，遇到对不上时别停在这两种解释上。

**只读分析与改包分发是两件事。** 前者不动原包、无签名问题；后者会让原签名失效、装不上原包、触发安全提示，还牵扯版权与分发边界。写结论时别把两者混在一句话里。

**结论落到地址或表行。** 每条判断标注它来自哪个函数、哪个地址、哪一行配置；推断与实测分开标。判定逻辑还原完之后，写个小还原器把界面文案重新生成一遍、与游戏里的实际显示逐条对上，才算自证闭环。
