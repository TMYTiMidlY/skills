# APK 与 native 库的静态逆向

从已发行的 APK 中还原"它到底按什么规则运行"。本文只讲跨应用通用的方法；完整实例见[爱养成系列](aiyangcheng.md)。

## <a id="app-structure"></a>应用结构探查

先按承载形式分层，再决定从哪里切入：

- **Java / Dex 层**：Activity、JNI 桥、广告、支付和系统能力。可用 jadx 一类反编译器查看源码级输出。
- **native 层**：Cocos2d-x、Unity il2cpp 等引擎可能把游戏逻辑放进 `lib/<abi>/*.so`。对采用这种结构的应用，这一层才是规则的主要所在地。
- **assets 层**：配置表、剧本和贴图，往往经过加密或编码。

先检查 `.so` 是否经过 strip（剥离符号）。保留符号的库会直接给出 C++ 类名和方法名；`nm -DSC` 输出的是已经还原可读名称的动态符号表，相当于作者留下的目录。拿到 `GameManager::readEndEvent()`、`EndLayer::checkEnd()` 这类符号后，按业务名词（`End`、`Reward`、`Shop`、`Save`）过滤，通常比在汇编里盲扫省事得多。

> Cocos2d-x 手游的 `libcocos2dcpp.so` 实测常常没有 strip，引擎类和业务类符号都在。这是常见形态，不保证普遍成立；遇到 strip 过的库，只能回到字符串与交叉引用。

引擎类应用的核心规则常落在 native 层而不是 Dex 层，但这不是定律。两层都扫一遍，再依据符号和调用链判断。

新旧组件混搭也是值得追的线索。一个包里同时出现远早于当代的签名证书和较新的 AndroidX / 广告 SDK，通常意味着"旧游戏本体 + 新发行壳"：本体逻辑在 native，壳负责接入。这只是线索，不是证据；按它分层后仍要用符号和调用链验证。

## <a id="asset-encryption"></a>资产加密的识别与批量解密

### <a id="algorithm-traces"></a>算法与密钥线索

解密算法通常直接写在符号表里。先找资产读取类的方法名，再顺着调用链看它调用了什么：

```text
CCSVParse::openFile()
  -> rc4_base64_decrypt(<key>, data)
```

符号名同时给出了算法（RC4）、编码层（Base64）和密钥参数位置。密钥多为硬编码常量，可跟着调用点的 `adrp` + `add` 取出字符串。

### <a id="ciphertext-diagnostics"></a>密文形态诊断

密文形态也能帮助缩小算法范围：

- Base64 解码后的长度**不按 16 字节对齐**时，可优先排除 AES-CBC / ECB 一类分组模式。**这条只在确认字节就是裸密文时成立**；若外层还包着头部、IV 或长度字段，对齐关系会被打乱，必须先剥掉封装再判断。
- 固定密钥的流密码（如 RC4）会让**相同明文前缀产生相同密文前缀**。据此可判断不同文件是否共用密钥：若一组文件带 UTF-8 BOM、另一组不带，两组密文从第一个字节起就分叉，这是明文差异，不是两套密钥，不要误判。

### <a id="batch-decryption"></a>批量解密与明文回退

批处理可以保留明文回退，但回退必须有门槛：先试 `Base64 → 解密`，失败后再按明文处理；**只有 UTF-8 解码成功才允许回退**。不能把任意解密失败的字节流静默写成明文，否则损坏文件会混进结果且无人察觉。实例见[爱养成的资产解密](aiyangcheng.md#asset-decrypt)。

## <a id="arm64-disasm"></a>native 库的反汇编与地址解析

目标环境可能没有 IDA、Ghidra 或 radare2，系统自带的 `objdump` 也可能只编译了 x86 后端，对 AArch64 报 `architecture: UNKNOWN!`。此时可以用反汇编引擎（如 Capstone）配合 ELF 解析库，构造满足当前分析需要的输出。依赖写进 PEP 723 内联脚本元数据，并用 `uv` 运行。

至少需要产出四类信息：完整指令流、字符串地址、符号化分支目标，以及文件偏移与虚拟地址的正确换算。

### <a id="instruction-stream"></a>指令流完整性

反汇编引擎遇到无法解码的字节时，通常会**静默停止**而不报错。一个几 MB 的 `.text` 段可能只解出前百分之几，调用方却毫不知情。AArch64 指令定长 4 字节，因此外层需要循环：内层迭代结束后检查游标是否到达段尾；没有到达，就前进 4 字节，从下一条重新扫描。

> 症状很隐蔽：交叉引用扫描返回空结果，看起来像"这个字符串没人引用"，实际是扫描器根本没有走到对应区域。自检时打印实际解出的指令数和最后一条地址，再与 `.text` 的起止地址对比；差距离谱就说明中途截断。
>
> ARM32 库（`armeabi-v7a`）还要处理 **Thumb 位**：函数符号的 `st_value` 最低位为 1，表示该函数使用 Thumb 指令集。反汇编前要清掉最低位作为地址，并切到 Thumb 模式；忽略它会得到整段乱码，而且同样不报错。

### <a id="string-addresses"></a>字符串地址恢复

AArch64 读取全局地址时需要两条指令配合：`adrp` 把 4 KB 页基址装入寄存器，`add`（或带立即数偏移的 `ldr`）补上低 12 位。分析器要维护"寄存器 → 页基址"映射；遇到 `add` 后合成完整地址，再到 `PT_LOAD`（可加载段）中读取 C 字符串并附在指令行末尾。没有这一步，汇编里只剩裸地址，很难阅读。

- 反汇编引擎输出的 `adrp` 立即数可能带 `#` 前缀。解析时若不剥掉，数值转换会抛异常；异常再被外层 `except` 吞掉后，映射表会一直为空，表现为"一条字符串注释都没有"。
- 每次跳过非法指令重新扫描时，都要清空寄存器映射。跨过未知区域后，先前记录的寄存器内容已不可信。

### <a id="branch-symbols"></a>分支目标符号化

`bl #0x413528` 本身没有业务含义；若注成 `CCString::createWithFormat`，就能立刻看出参数可能是格式串。建立"地址 → 符号名"映射，对 `bl` / `b` 的立即数目标查表并附注符号。

### <a id="elf-addresses"></a>ELF 文件偏移与虚拟地址

ELF 的文件偏移与虚拟地址是两套坐标。`strings -td` 给出的是**文件偏移**；段的 `p_vaddr` 与 `p_offset` 通常只在第一个 `PT_LOAD` 段相等，后续段会错开。若把 `strings` 的数字直接当作虚拟地址做交叉引用，结果会是空的。要么读取段表完成换算，要么在自己解析出的字符串表中按内容查询地址。

## <a id="ui-to-data"></a>从界面文案反查数据与代码

### <a id="lookup-chain"></a>文案到调用点的反查链

用户能看到的一句话，往往是进入代码最省力的入口：

```text
界面文案 → 含它的资源文件 → 文件路径字符串在库里的地址
         → 交叉引用找到读取该文件的取值器
         → 反查取值器的所有调用点并读取常量下标
         → 落到具体的界面函数
```

关键是查"取值器 + 下标"，而不是直接查文案。文案通常存在 plist / JSON 资源里，代码只保留 `RB(int index)` 一类按下标取值的函数。先对资源文件路径字符串做交叉引用（xref），定位取值器；再扫描全库中的 `bl <取值器>`，记录调用点前几条指令装入 `w0` 的立即数，就能得到"哪个函数用了第几条文案"的映射表。要找一句话在哪里弹出，查表即可。

### <a id="renderer-classification"></a>渲染函数的缺失条件定性

"界面没有显示某条件"必须读渲染函数才能定性。已经实测到的成因至少有两种：

- **该字段的渲染分支不存在**：渲染函数没有处理这个键，因此该字段对所有条目都不显示。
- **存在硬编码黑名单**：渲染函数先把条目 ID 与内联数组比较；命中后显示"特殊 / 敬请期待"一类兜底文案并直接返回，跳过全部数值渲染。

两种情况在数据表里看起来完全一样：字段都有值，只有渲染函数能区分。也不排除还有别的成因；遇到解释不通的条目，不要停在这两种可能上。

黑名单常见形态是把若干字符串常量放进可变参数数组，再调用 `containsString(array, id)`：

```text
arrayWithObjects("A","B","C", …, NULL)
if (containsString(list, itemId)) → 显示兜底文案，return
else                              → 逐字段拼描述
```

这些常量在反汇编里通常表现为连续的 `adrp` + `add`，容易识别。黑名单本身就是一份可复核的清单；具体实例及其隐藏范围见[爱养成的结局面板渲染](aiyangcheng.md#panel-rendering)。作者为何圈定这些条目属于推测，不应混进事实结论。

### <a id="reconstruction-check"></a>还原器闭环验证

每条判断都要落到函数、地址或配置表行，并把实测与推断分开标。判定逻辑还原后，可以写一个小还原器重新生成界面文案，再与应用的实际显示逐条对照。只有数据读取、规则理解和渲染结果能互相印证，证据链才闭合。

## <a id="rule-table-semantics"></a>数值规则表的语义还原

配置表（CSV / plist）通常以一行表示一条规则，但每个单元格的含义必须从判定函数读取，不能只靠表面文字猜测。

### <a id="cell-semantics"></a>单元格与比较方向

**空单元格与零不是一回事。** 判定循环通常先跳过空单元格，表示不检查这一项；零则是真实门槛。把空值当作 0 会凭空制造约束。

**符号可能编码上下界。** 常见形态是正数表示下界（玩家值 ≥ 要求），负数表示上界（玩家值 ≤ 绝对值）。判定函数中会出现"按符号位分支，一支比较 `ge`、另一支比较 `le`，负数分支先取绝对值"的结构。

**界面措辞常与真实比较符不一致。** 界面可能拼成 `属性>600`，判定却使用 `cinc ..., ge`（≥）。边界值相差 1 点就可能改变结果，因此应以判定函数为准，界面文案只作参考。

### <a id="match-order"></a>匹配顺序与优先级

如果规则按行扫描，并以"满足项计数 == 需检查项计数"作为命中条件，就意味着**表中靠前的行优先胜出**。这会出现"目标条件全部达标，却得到另一个结果"的情况：前序规则先命中了。分析某条规则如何达成时，必须同时判断它之前哪些行可能与它共同成立。

### <a id="overlap-analysis"></a>规则重叠与规避区间

前序规则的重叠可以机械化计算：把每行折算成 `{属性: (下界, 上界)}`，再与目标行逐属性求交。若某属性的交集下界大于上界，两行结构互斥，不可能同时命中；否则先列为候选威胁。随后叠加非数值条件，例如互斥的前置事件、额外解锁项或付费项，再做二次剔除。剩下的才是需要提醒用户规避的规则。

规避建议要给出具体区间。优先寻找"目标行完全不检查、威胁行却强制要求"的属性：把它控制在威胁行无法命中的区间，不会影响目标行，相当于免费的隔离带。

## <a id="offline-service-repair"></a>失效在线服务的本地替代

停服后支付界面可能仍在，但支付 SDK 或服务器已经失效。先确认发货逻辑位于哪一层：很多游戏原本就在 native 支付回调中按商品 ID 更新金币、解锁项并保存存档，Java 支付层只是传递"成功"信号。

若调用链属于这种结构，最小改动是在 Java 层把失效的传输调用短接到**原版已有的成功回调**。参数必须沿用原版购买成功路径；有的版本带第二个参数，例如表示数量的常数。自行编造参数可能进入另一条分支。这个改法不动 native 库，也不改商品编号、价格文字或存档实现，只替换传输段。两代实例见[停服后商城的本地发货](aiyangcheng.md#store-repair)。

## <a id="build-verify"></a>改包的构建、签名与成品验证

### <a id="target-smali"></a>多 Dex 目标定位

多 Dex 包不能假定目标类总在 `smali/`。应按类的包路径在解包目录中搜索：

```bash
find <decoded-apk> -path '*/<包路径>/<Target>.smali'
```

命中哪个 `smali_classesN/`，就修改哪个目录中的类。

### <a id="package-pipeline"></a>构建与成品验证

改包会使原签名失效，需要重新 zipalign，并按目标系统选择签名方案；v2 / v3 的适用范围随 Android 版本而变，不是一律全部启用。

签名工具报告成功，只能证明签名结构自洽，既不能证明目标设备一定能安装，也不能证明修改进入了最终 Dex。最后必须从**签名后的成品**中反编译目标类，确认预期调用确实存在。这样能抓住改错 Dex、复用旧产物、编辑未被打包的目录、签名时选错文件等问题。

以下工具链和参数已按所列版本验证；更换版本前先确认参数仍然存在：

```bash
# 解包。-r = 不解码资源，只改 smali 时更快也更少出岔子
java -jar apktool.jar d -f -r -o <decoded-apk> <input.apk>

# 改 <decoded-apk>/smali_classes*/<包路径>/<Target>.smali

java -jar apktool.jar b <decoded-apk> -o <unsigned.apk>
unzip -tq <unsigned.apk>          # 压缩包完整性自检

# zipalign + 签 v2/v3 + 验证，一步完成；--allowResign 允许覆盖已有签名
java -jar uber-apk-signer.jar -a <unsigned.apk> -o <signed-dir> --allowResign

# 只反编译目标类，比整包快得多
jadx --single-class <包名>.<Target> --single-class-output <Target>.java <signed.apk>
```

> 实测版本：[Apktool 2.9.3](https://github.com/iBotPeaches/Apktool/releases/tag/v2.9.3)、[uber-apk-signer 1.3.0](https://github.com/patrickfav/uber-apk-signer/releases/tag/v1.3.0)、[jadx 1.5.1](https://github.com/skylot/jadx/releases/tag/v1.5.1)。

### <a id="resign-boundaries"></a>重签名边界

- 重签名包不能覆盖原签名安装，必须先卸载原包，因此必须先解决数据导出，见[设备侧取数通道](adb.md)。
- 新证书不再是官方发行证书。安装器、安全中心或扫描器可能提示"非官方签名""来源未知""存在风险"，**具体文案取决于设备和安装器**。这些提示**不能证明包内含有恶意代码**，只说明系统无法用官方签名确认发布者；仍需依靠可信来源、哈希和可复现构建判断。
- 签名密钥需要长期保留，否则后续更新会再次遇到签名不一致。

分发或安装前，记录原包哈希、改包哈希、签名证书指纹，以及对应源码或补丁版本。

## <a id="save-data"></a>存档实现与文件定位

游戏可能自带存档实现，而不使用引擎默认设施。先找存档类符号，例如 `saveProfile` 或 `UserDefault` 的自定义变体，再沿调用链确认它写入的文件名。典型形态是主文件加一个写入时生成的滚动备份：

```text
<Name>.bin
<Name>.bin.bac
```

Android 运行时通常把它们放在 `/data/user/0/<package>/files/`。引擎自带的 `UserDefault.xml` 往往只保存附加偏好，不能替代主存档。

静态分析负责确认"哪些文件才是存档"；卸载前如何实际取到主文件与备份、记录大小和哈希，以及如何验证备份覆盖范围，统一见[迁移前置检查](adb.md#migration-prerequisites)。
