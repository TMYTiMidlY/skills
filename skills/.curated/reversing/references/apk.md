# APK 与 native 库的静态逆向

从一个已发行的 APK 里把"它到底按什么规则运行"读出来。方法与应用无关；具体应用的实例见 [爱养成系列](aiyangcheng.md)。

## <a id="app-structure"></a>应用结构探查

拿到包先分层，不同层用不同手段：

- **Java / Dex 层**：Activity、JNI 桥、广告、支付、系统能力。用 jadx 一类反编译器直接看源码级输出。
- **native 层**：Cocos2d-x、Unity il2cpp 等引擎把游戏逻辑放在 `lib/<abi>/*.so` 里。这才是规则的真正所在地。
- **assets 层**：配置表、剧本、贴图。往往加密。

**先看 `.so` 有没有 strip。** 保留符号的库直接给出 C++ 类名和方法名，`nm -DSC` 的输出（解 mangle 后的动态符号表）就是可读的目录。拿到 `GameManager::readEndEvent()`、`EndLayer::checkEnd()` 这类符号，等于拿到作者写的章节名；按业务名词（`End`、`Reward`、`Shop`、`Save`）过滤符号表，比在汇编里大海捞针省事得多。

> Cocos2d-x 手游的 `libcocos2dcpp.so` 实测常常不 strip，引擎类和业务类符号全在。这是常见形态，不保证普遍成立——遇到 strip 过的库只能回到字符串与交叉引用。

**新旧组件混搭是值得追的线索。** 一个包里同时有远早于当代的签名证书和最新的 AndroidX / 广告 SDK，通常意味着"旧游戏本体 + 新发行壳"：本体逻辑在 native、壳只负责接入。这是线索不是证据，按它分层之后仍要用符号和调用链验证。

## <a id="asset-encryption"></a>资产加密的识别与批量解密

**解密算法通常直接写在符号表里。** 找资产读取类的方法名，顺着调用链看它调了什么：

```text
CCSVParse::openFile()
  -> rc4_base64_decrypt(<key>, data)
```

符号名同时给出了算法（RC4）、编码层（Base64）和密钥参数位置。密钥多为硬编码常量，跟着调用点的 `adrp`+`add` 取字符串即可。

**从密文形态反推算法**，几条能快速缩小范围的诊断：

- 解 Base64 后长度**不按 16 字节对齐** → 可优先排除 AES-CBC/ECB 一类分组模式。**这条只在确认字节就是裸密文时成立**——若外面还裹着头部、IV 或长度字段，对齐关系会被打乱，得先剥掉封装再判断。
- 固定密钥的流密码（RC4）会让**相同明文前缀产生相同密文前缀**。据此可判断不同文件是否共用密钥：若一组文件带 UTF-8 BOM、另一组不带，两组密文从第一个字节起就分叉——这是明文差异，不是两套密钥，别误判。

**批处理要留回退，但回退必须有门槛。** 先试 `Base64 → 解密`，失败再当明文；**回退以 UTF-8 解码成功为准**，不能把任意解密失败的字节流静默当明文写出去，否则损坏文件会混进结果且无人察觉。实例见 [爱养成的资产解密](aiyangcheng.md#asset-decrypt)。

## <a id="arm64-disasm"></a>缺少成套工具时读 native 库

目标环境常常没有 IDA / Ghidra / radare2，系统自带的 `objdump` 又往往只编了 x86 后端（对 aarch64 报 `architecture: UNKNOWN!`）。这时可以用一个反汇编引擎（如 Capstone）加 ELF 解析库自己拼一个够用的，依赖写进 PEP 723 内联脚本元数据、用 `uv` 跑。

需要产出的东西有四样，每样都对应一个真实的坑：

**一份没有中途截断的指令流。** 反汇编引擎撞上无法解码的字节通常**静默停止**、不报错。一个几 MB 的 `.text` 可能只解出前百分之几就悄悄结束，而调用方毫不知情。AArch64 指令定长 4 字节，所以要在外层套循环：内层迭代结束后检查游标是否到达段尾，没到就 +4 从下一条重新起扫。

> 症状极隐蔽：交叉引用扫描返回空结果，看起来像"这个字符串没人引用"，实际是扫描器根本没走到那一段。自检办法是打印实际解出的指令数与最后一条的地址，与 `.text` 的起止对比——差得离谱就是被截断了。
>
> ARM32 库（`armeabi-v7a`）还要额外处理 **Thumb 位**：函数符号的 `st_value` 最低位为 1 表示该函数是 Thumb 指令集，反汇编前要把这一位清掉当地址、并按 Thumb 模式解码。忽略它会得到整段乱码，且同样不报错。

**带字符串注释的指令行。** AArch64 取全局地址要两条指令配合：`adrp` 把 4KB 页基址装进寄存器，`add`（或 `ldr` 的立即数偏移）补低 12 位。要维护"寄存器 → 页基址"的映射，遇到 `add` 就合成完整地址、去 `PT_LOAD` 段里读 C 字符串贴在行尾。没有这一步，汇编里全是裸地址，读不动。

- 反汇编引擎输出的 `adrp` 立即数可能带 `#` 前缀，解析时要剥掉，否则数值转换抛异常、被外层 `except` 吞掉，映射表永远是空的——现象同样是"字符串注释一条都不出来"。
- 每次跳过非法指令重新起扫时清空寄存器映射：跨过未知区域后寄存器内容不可信。

**符号化的分支目标。** `bl #0x413528` 无意义，注上 `CCString::createWithFormat` 就一眼看出参数是格式串。建一张"地址 → 符号名"表，对 `bl` / `b` 的立即数目标查表贴注释。

**正确的地址换算。** ELF 里文件偏移与虚拟地址是两套。`strings -td` 给的是**文件偏移**；段的 `p_vaddr` 与 `p_offset` 通常只在第一个 `PT_LOAD` 段里相等，后面的段会错开。拿 `strings` 的数字直接当地址做交叉引用，扫出来一定是空的。要么读段表做换算，要么在自己解析出的字符串表里按内容查地址。

## <a id="ui-to-data"></a>从界面文案反查数据与代码

用户能看到的一句话，是切进代码最省力的入口。链路固定：

```text
界面文案 → 含它的资源文件 → 文件路径字符串在库里的地址
         → xref 找到读取该文件的取值器
         → 反查取值器的所有调用点、看常量下标
         → 落到具体的界面函数
```

**关键技巧是查"取值器 + 下标"而不是查文案本身。** 文案通常存在 plist / json 资源里，代码里只有一个 `RB(int index)` 之类的按下标取值函数。所以：先 xref 资源文件路径字符串，定位到取值器；再扫全库找 `bl <取值器>`，把调用点前几条指令里装进 `w0` 的立即数记下来，就得到"哪个函数用了第几条文案"的全表。想找哪句话在哪弹出来，查表即可。

**"界面没显示某条件"要读渲染函数才能定性。** 已实测到的两种成因：

- **该字段的渲染分支根本不存在**——渲染函数里就没处理这个键。这类字段对所有条目都不显示。
- **有硬编码黑名单**——渲染函数开头拿条目 ID 比对一个内联数组，命中就走"特殊 / 敬请期待"之类的兜底文案，直接 return，跳过全部数值渲染。

两者在数据表里长得一模一样（字段填得好好的），只有读渲染函数能分清；也不排除还有别的成因，别停在这两种解释上。黑名单一般长这样：把若干字符串常量塞进一个可变参数数组，然后 `containsString(array, id)`：

```text
arrayWithObjects("A","B","C", …, NULL)
if (containsString(list, itemId)) → 显示兜底文案，return
else                              → 逐字段拼描述
```

这几个常量在反汇编里是连续的 `adrp`+`add`，非常好认。**黑名单本身就是一份清单**：被显式排除在条件展示之外的那批条目，实测往往正好是隐藏要素的全集（见 [爱养成的面板黑名单](aiyangcheng.md#panel-rendering)）；至于作者为何这样圈定属于推测，不必写进结论。

## <a id="rule-table-semantics"></a>数值规则表的语义还原

配置表（CSV / plist）里的一行 = 一条规则，但"这个格子是什么意思"必须从判定函数里读，不能猜。要还原的几件事：

**空格与零不是一回事。** 判定循环通常先跳过空单元格（不检查此项），零则是一个真实的门槛值。把空格当 0 处理会凭空造出一堆约束。

**符号可能编码方向。** 常见做法是用正负号区分上下界：正数 = 下界（玩家值 ≥ 要求），负数 = 上界（玩家值 ≤ 绝对值）。判定函数里会看到"取符号位分支 → 一支比 `ge` 一支比 `le`、且负数分支先取绝对值"的结构。

**界面措辞常与真实比较符不一致。** 界面拼成 `属性>600`，判定用的却是 `cinc ..., ge`（≥）。差 1 点在边缘 build 上就是过与不过。以判定函数为准，界面文案只作参考。

**多条规则的匹配顺序决定归属。** 逐行扫描 + "满足项计数 == 需检查项计数"就算命中的结构，意味着**表中靠前的行优先胜出**。于是会出现"条件全部达标却拿到另一个结果"——被前面某行截胡了。分析某条规则怎么达成时，必须连带算出：它前面哪些行可能与它同时成立。

**判定式的截胡分析可以机械化。** 把每行折算成 `{属性: (下界, 上界)}`，与目标行逐属性求交；下界 > 上界即结构互斥、永不可能截胡，否则就是候选威胁。再叠加非数值条件（互斥的前置事件、需要额外解锁 / 付费的项）做二次剔除。剩下的才是真正要提醒用户规避的。

**规避杠杆要给具体区间。** 找出那些"目标行完全不检查、而威胁行强制要求"的属性——它就是免费的隔离带，把它卡在威胁行够不到的区间即可，且不影响目标行。

## <a id="offline-service-repair"></a>失效在线服务的本地替代

停服后支付 UI 还在，但支付 SDK / 服务器已死。**先确认发货逻辑在哪一层**：很多游戏的商品发放本来就在 native 的支付回调里完成（按商品 ID 更新金币、解锁项，再存档），Java 支付层只是"成功"信号的传输通道。

如果是这种结构，最小改动就是在 Java 层把失效的传输调用，短接到**原版自己已有的成功回调**上。参数要照抄原版购买成功路径（有的版本带第二个参数，比如表示数量的常数），不要自己编——编出来的参数可能落进另一条分支。这个改法不动 native 库、不改商品编号 / 价格文字 / 存档实现，只替换了传输段。具体到某作的两代改法见 [停服后商城的本地发货](aiyangcheng.md#store-repair)。

## <a id="build-verify"></a>改包的构建、签名与成品验证

**多 Dex 包要先定位目标类真正落在哪个 smali 目录**，不能假定总在 `smali/`——按类的包路径在解包目录里搜一遍（`find <decoded-apk> -path '*/<包路径>/<Target>.smali'`），命中哪个 `smali_classesN/` 就改哪个。

**改包后原签名失效**，需要重新 zipalign 并按目标系统选择签名方案（v2/v3 的适用范围随 Android 版本而定，不是一律都要）。**签名工具报成功只证明签名结构自洽**，既不证明目标设备一定装得上，也不证明你的修改进了最终 Dex。所以最后一步固定是：从**签名后的成品**里反编译目标类，确认期望的调用真的在里面。这一步能抓住改错 Dex、复用旧产物、编辑了未被打包的目录、签名时拿错文件这几类错误。

一套验证过的工具链与关键参数（版本锁在实测过的那一版；换版本前先确认参数还在）：

```bash
# 解包。-r = 不解码资源，只改 smali 时更快也更少出岔子
java -jar apktool.jar d -f -r -o <decoded-apk> <input.apk>

# 改 <decoded-apk>/smali_classes*/<包路径>/<Target>.smali

java -jar apktool.jar b <decoded-apk> -o <unsigned.apk>
unzip -tq <unsigned.apk>          # 压缩包完整性自检

# zipalign + 签 v2/v3 + 验证，一步完成；--allowResign 允许覆盖已有签名
java -jar uber-apk-signer.jar -a <unsigned.apk> -o <signed-dir> --allowResign

# 只反编译目标那一个类，比整包快得多
jadx --single-class <包名>.<Target> --single-class-output <Target>.java <signed.apk>
```

> 实测版本：[Apktool 2.9.3](https://github.com/iBotPeaches/Apktool/releases/tag/v2.9.3)、[uber-apk-signer 1.3.0](https://github.com/patrickfav/uber-apk-signer/releases/tag/v1.3.0)、[jadx 1.5.1](https://github.com/skylot/jadx/releases/tag/v1.5.1)。

**重签名包的边界要如实告知：**

- 不能覆盖原签名安装，必须先卸载（于是先要解决数据导出，见 [设备侧取数通道](adb.md)）。
- 证书不再是官方发行证书，安装器 / 安全中心 / 扫描器可能提示"非官方签名""来源未知""存在风险"——**具体文案取决于设备和安装器**。这类提示**不能证明含恶意代码**，只说明系统无法用官方签名确认发布者；用户仍需靠可信来源、哈希和可复现构建判断。
- 签名密钥要长期保留，否则自己的后续更新会再次遇到签名不一致。

分发或安装前记录：原包哈希、改包哈希、签名证书指纹、对应源码或补丁版本。

## <a id="save-data"></a>存档文件定位

游戏常自带存档实现而不用引擎默认设施。找存档类的符号（`saveProfile`、`UserDefault` 的自定义变体等），顺着看它写什么文件名。典型形态是主文件加一个写入时生成的滚动备份：

```text
<Name>.bin
<Name>.bin.bac
```

Android 内部路径通常是 `/data/user/0/<package>/files/`。引擎自带的 `UserDefault.xml` 往往只存附加偏好，不能替代主存档。

**卸载原签名包之前，必须实际取到主文件和备份文件，并记录大小与哈希。** 只确认 `allowBackup=true`、或看到备份工具跑成功，都不构成"数据已到手"。
