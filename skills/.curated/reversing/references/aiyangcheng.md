# 爱养成系列

《爱养成》系列 Android 重打包版的完整还原记录：资产如何解密、规则表如何解释、结局判定落在哪些函数，以及**用户问"某结局怎么达成"时应按什么格式回答**。

> 实测快照：《爱养成2》2.9.7.4（`cn.actcap.ayc2`）、《爱养成3》1.7.4（`cn.actcap.ayc3`）。结论均由反汇编、解密后的资产、成品反编译或真机操作验证。通用方法见[APK 与 native 库的静态逆向](apk.md)。

## <a id="structure"></a>应用结构

两代主体都是 Cocos2d-x C++：

- 游戏逻辑集中在 `lib/armeabi-v7a/libcocos2dcpp.so` 和对应的 `arm64-v8a` 库。这些库**没有 strip**，`GameManager`、`Player`、`EventLayer`、`EndLayer`、`PlaceLayer`、`PhotoAlbumLayer`、`CCSVParse`、`IapStore` 等 C++ 符号全部保留，因此符号表是本实例的首要入口。
- Java / Dex 层主要承担 Activity、JNI 桥接、广告、支付和系统能力；`com.catcap.Catcap` 是 C++ → Java 的主要桥。
- 包内同时存在 AndroidX、穿山甲广告 SDK 等较新组件，而签名密钥创建于 2014 / 2015 年，呈现出典型的"旧游戏本体 + 新发行壳"结构。

## <a id="asset-decrypt"></a>资产解密

调用链直接写在符号表中：

```text
CCSVParse::openFile()
  -> rc4_base64_decrypt("dhopNVDUg97ijxDe", data)
```

解密流程是 `plaintext = RC4(key, Base64Decode(assetBytes))`，两代共用同一个密钥。

| 作品 | CSV 数量 | 位置 |
|---|---:|---|
| 爱养成2 | 2172 | `assets/*.csv` |
| 爱养成3 | 1302 | `assets/ios_chs/csv/`、`assets/ios_cht/csv/` |
| 合计 | 3474 | |

简体文件通常带 UTF-8 BOM，繁体 `_ft` / `ios_cht` 文件不带，因此两组密文从第一个字节起就不同。这是明文差异，不是两套密钥。批量解密以"UTF-8 解码成功"作为明文回退门槛；实测 3469 个文件经过 RC4 解密，5 个文件原本就是明文，可以全量还原且没有误判。

## <a id="data-model"></a>数据模型

CSV 分为剧本文件和规则表，两类文件混在同一目录中，可以根据第一行区分：**规则表第一行通常是中文字段名，剧本文件第一行直接是指令**。

### <a id="scenario-files"></a>剧本文件

剧本是一套轻量的行驱动虚拟机（VM），列为：

```text
say emote in out scene music cgin cgout word reward choose fin
```

分支写成 `rewardId||选项文本||跳转行号`；文本支持 `$kidname` 一类变量插值，`|` 表示分页或换段。两代合计约 40270 行剧本指令。

### <a id="rule-files"></a>规则表

规则表相当于随包附带的设计文档：

- `goout.csv` / `celebration.csv` / `workbook.csv`：地点、时间、前置事件、优先级、课程 / 打工次数和属性阈值。
- `end.csv`：结局判定条件，是本文重点。
- `reward.csv`：属性、货币、角色好感度和解锁项的增量。
- 《爱养成3》另有 `monster.csv`、`wing.csv`、`piece.csv`，覆盖战斗、翅膀和服装碎片。

### <a id="route-files"></a>男女主线文件分流

男女主线通过文件名后缀分流。`GameManager::AddBoy()` 根据存档中的性别字段，把 `<name>.csv` 替换为 `<name>_boy.csv`，使用的格式串是 `%s_boy.%s`。因此，男主线读取 `end_boy.csv`、`goout_boy.csv`，女主线读取无后缀版本，两套表互不影响。

### <a id="attribute-models"></a>属性模型

两代属性模型不同：

```text
爱养成2：体力 智力 武力 法力 气质 魅力 体贴 道德 感受 叛逆
爱养成3：体力 疲劳 魔力 武力 智力 魅力 体贴 技能 光属性 暗属性
```

## <a id="ending-tables"></a>结局表结构与判定语义

### <a id="ending-columns"></a>列结构

`end.csv` / `end_boy.csv` 使用中文行与英文行两行表头：

```text
编号 结局名称 体力 疲劳 魔力 武力 智力 魅力 体贴 技能 知名度 黑暗 金币
npc编号 好感度 修炼 次数 必要事件 必要服装 冒险次数 艾泽尔 切西亚 光暗礼包 魔精灵礼包
endID name energy tired magic force iq glamour thoughtfulness raise popular dark coins
npc love class times necessary cloth adventure azel chelsea packa packb
```

### <a id="ending-evaluation"></a>判定语义

以下语义来自 `EndLayer::checkEnd()`：

- **空单元格 = 不检查**。判定循环先跳过空值，不把它计入"需满足项"。
- **正数 = 下界**（玩家值 ≥ 要求）；**负数 = 上界**（玩家值 ≤ 绝对值）。汇编中先按符号位分支，负数分支取绝对值后再比较 `le`。
- `npc` + `love` 成对：指定角色的好感度 ≥ `love`。
- `class` + `times` 成对：指定课程或打工安排次数 ≥ `times`。
- `necessary`：玩家的已触发事件列表中**必须包含**该事件 ID，由 `containsString` 判定。
- `azel` / `chelsea` / `packa` / `packb`：需要解锁对应角色剧情，或购买对应礼包。
- **规则逐行扫描，"满足数 == 需检查数"即命中，表中靠前的行先胜出。** 这是前序结局截胡目标结局的根源。

## <a id="panel-rendering"></a>结局面板的渲染

图鉴中点击大图后弹出的条件说明由 `PhotoAlbumLayer::onBigPhoto()` 生成。理解"面板条件为什么与真实判定不一致"需要同时看条目黑名单和字段渲染范围。

### <a id="ending-blacklist"></a>条目黑名单

函数开头先检查一张硬编码 ID 黑名单：

```text
arrayWithObjects("760","730","705","715","716","744","745","746", NULL)
if (containsString(list, endID)) → 显示 RBS[6] = "特殊结局~ "，直接返回
else                            → 逐字段拼条件文案
```

这八个 ID 是**四对对称的男女结局**：女 705 / 715 / 716 / 730 ↔ 男 744 / 745 / 746 / 760。可观察事实是，这批条目的条件展示被代码明确跳过，而且它们恰好构成隐藏要素的全集。作者为何这样圈定属于推测，不写入结论。对还原工作而言，这张表本身就是一份隐藏要素清单。

### <a id="ending-fields"></a>字段渲染范围

非黑名单条目会逐字段拼接文案，但只覆盖部分字段：

| 字段 | 渲染成 | 备注 |
|---|---|---|
| `AttributeName.plist` 中的键 | `体力>600` / `体贴<300` | 包含 energy tired magic force iq glamour thoughtfulness raise popular dark **coins**；正数用 `>`，负数用 `<` 加绝对值 |
| `npc` + `love` | `苏瑞尔的友好度大于4心` | 心数 = `ceil(love × 0.5)`，即好感 8 显示为 4 心 |
| `class` + `times` | `安排魔法次数大于30次` | 课程名查询 `classname.plist` |
| `azel` / `packa` / `packb` | `需要解锁艾泽尔剧情` / `需要购买光暗礼包` / `需要购买魔精灵礼包` | 固定文案 |
| `necessary`、`cloth`、`adventure`、`chelsea` | **没有渲染分支** | 对**所有**结局都不显示 |

### <a id="ending-operators"></a>显示符号与真实比较

面板中的 `>` / `<` 实际对应 `≥` / `≤`。判定使用 `cinc ..., ge` / `cinc ..., le`，界面措辞相差一个边界值，因此边缘数值必须以判定函数为准。

隐藏由两层构成：黑名单条目会隐藏**整条**条件；即使条目不在黑名单中，`necessary` 等没有渲染分支的字段仍然不会显示。

## <a id="event-branch"></a>代码生成的事件分支

有些 `necessary` 引用的事件 ID 在任何 CSV 中都找不到定义，因为它们由代码生成。《爱养成3》的 `PlaceLayer::onEventFin()` 包含一张 `switch`；某个事件播放结束后会调用：

```text
addChooseEvent(<触发事件ID>, <选项A事件ID>, <选项B事件ID>)
```

按钮贴图是 `map/choose_<触发事件ID>_a.png` / `_b.png`，男主线再加 `_boy` 后缀。查看贴图即可确认两个选项的原文。**A 绑定第二个参数，B 绑定第三个参数**：反汇编中 `w2` 先装入 A 的回调 tag，`w3` 装入 B 的回调 tag。

这类二选一**不可回头且互斥**。同一次选择产生的两个事件 ID 不可能同时出现在存档的已触发列表中；若两条结局分别要求这两个 ID，它们就是结构互斥，无需再计算数值交集。

## <a id="report-format"></a>结局达成条件的汇报格式

用户问"某结局怎么达成 / 需要什么条件"时，按以下三张表依次回答。只报告目标行的数值，会漏掉两类致命信息：面板不显示的隐藏门槛，以及先于目标行命中的结局。

### <a id="report-target"></a>目标结局表

第一张是固定六行的纵表：

| 项 | 填写要求 |
|---|---|
| **面板描述（游戏内）** | 逐字写出玩家实际看到的原文；黑名单条目写 `特殊结局~ ` |
| **面板本该显示的文案（按原渲染规则还原）** | 绕过整条黑名单后，用还原器按原字段渲染规则生成；原函数没有渲染分支的字段仍不会出现在这里 |
| **真实要求** | 写出判定函数使用的完整条件，用 ≥ / ≤ 标明方向，并补齐面板不显示的字段 |
| **无要求项** | 显式列出所有"不检查"的属性，为后续寻找规避杠杆提供依据 |
| **前置事件怎么拿** | 给出事件链、分支选项原文，以及不可回头或互斥的提醒 |
| **代码依据** | 标出面板黑名单、判定和事件分支所在函数，并注明目标表行 |

### <a id="report-preempt"></a>前序结局筛查表

第二张表按实际扫描顺序列出**目标行之前的每一行**，一行都不省。用户需要看见哪些结局已经检查过、为什么被排除。

| 编号 | 名称 | 面板描述（游戏内原文） | 面板未显示的门槛 | 对目标的威胁 |
|---|---|---|---|---|

"对目标的威胁"使用以下固定词汇，并紧跟客观理由：

- `永不可能`：数值区间互斥，要写明哪个属性的上下界冲突。
- `结构互斥`：两行分别要求同一次二选一产生的互斥事件。
- `高危` / `中危`：数值上可能同时成立。分级依据必须写成客观事实，例如"数值门槛被目标行完全包含，只差某两项"，不要只给主观标签。
- `门槛够不着`：某属性要求远高于当前周目的合理范围。这个结论依赖玩家养成路线的假设，属于推断，必须标明前提。

### <a id="report-safezone"></a>威胁结局与规避方案表

第三张表只展开前一张表中判定为 `高危` / `中危` 的结局：

| 编号 | 名称 | 完整条件 | 与目标的重叠或冲突 | 可用规避杠杆 |
|---|---|---|---|---|

- **完整条件**与目标结局使用同一口径：包含数值、好感、事件、解锁和礼包条件，方向统一写成 ≥ / ≤，用户应能直接照着规避。
- **可用规避杠杆**优先选择"目标行完全不检查、威胁行却强制要求"的属性，并给出威胁行无法命中的具体区间。它不影响目标行，是免费的隔离带。
- 表后单列能够同时隔离多条威胁的**整体安全区**，再给出至少一个备选方案及其代价，让用户可以权衡。

### <a id="report-evidence"></a>证据与表述要求

- 每条结论就近标出来源函数、地址或表行；实测与推断分开标。例如，时间列的 `年|月|日` 解读若来自表内模式，就明确说明没有代码直接佐证。
- 面板文案必须由**还原器生成**，不能手抄 CSV。还原器同时用于验证对渲染规则的理解。
- 前序结局分析要机械化计算：逐属性求上下界交集，不能凭印象判断"这个应该不会冲突"。

### <a id="case-threats"></a>威胁结局与规避方案

"门槛够不着"依赖低暗周目的假设；如果刻意堆高暗属性，那些结局会重新成为威胁。本例需要进一步展开 739、742、743：

| 编号 | 名称 | 完整条件 | 与目标的重叠或冲突 | 可用规避杠杆 |
|---|---|---|---|---|
| 743 | 巫师夫妻 | 体力≥500、魔力≥600、武力≥500、智力≥300、魅力≥300、体贴≥300、**暗属性≥300**、**切西亚(man5)好感≥8** | 凑齐 744 的六项数值时，743 的七项数值自动达标，只差暗达到 300 和切西亚好感达到 8 | 暗属性≤299 |
| 742 | 大主教 | 体力≥500、魔力≥600、武力≥400、**智力≥600**、魅力≥400、体贴≥450、**知名度≥700**、**暗属性≤100** | 相对 744 只多要求智力 600 和知名度 700 | 暗属性≥101 |
| 739 | 旅人 | 魔力≥500、武力≥600、**智力≥600**、**魅力≥700**、体贴≥500、**暗属性≥300**、**艾泽尔(man6)好感≥8**、**需解锁艾泽尔剧情** | 数值上可能与 744 同时成立，且依赖艾泽尔路线 | 暗属性≤299 |

**整体安全区**：把暗属性控制在 **101–299**。742 要求 ≤100，739 / 743 要求 ≥300，其余前序结局都要求 ≥600；这个区间可以同时隔离它们，而且 744 本身不检查暗属性。

**备选方案及代价**：暗属性可以 ≤100，但知名度要压在 700 以下，这只能阻断 742；它会失去对 739 / 743 的隔离，因此还要另行控制切西亚 / 艾泽尔好感。

### <a id="case-time-field"></a>时间字段的解释边界

> 时间列的 `3|7.8.9.10.11.12|n` 按"第 3 年 7–12 月"解读，是从表内模式推的，没有代码直接佐证。

## <a id="save-file"></a>存档文件与迁移

### <a id="save-layout"></a>文件结构

游戏自写的 `WhyUserDefault` 默认使用以下文件名：

```text
WUD_Default.bin
WUD_Default.bin.bac
```

`WUD_Default.bin` 包含 `playerInfo`、金币、衣柜、事件、结局和照片 ID 等数据；`.bac` 是写入时生成的滚动备份。Cocos2d-x 的 `UserDefault.xml` 只保存附加偏好，不能替代主存档。Android 内部路径通常为：

```text
/data/user/0/<android-package>/files/WUD_Default.bin
```

### <a id="save-migration-set"></a>迁移文件清单

两代结构相同，但 `cn.actcap.ayc2` 与 `cn.actcap.ayc3` 各有独立文件，不能混用：

| 文件 | 作用 | 是否迁移 |
|---|---|---|
| `files/WUD_Default.bin` | 主存档 | 必须 |
| `files/WUD_Default.bin.bac` | 滚动备份 | 必须；主档损坏时可改名顶替 |
| `files/UserDefault.xml` | 音乐、语言等偏好 | 可选 |
| `shared_prefs/anti_key.xml` | 防沉迷状态 | 可选 |
| `shared_prefs/first_key.xml` | 首次确认状态 | 可选 |
| `shared_prefs/pay_request_ids.xml` | 旧支付待处理订单 | **不要迁移** |

### <a id="save-compatibility"></a>重签名版本兼容性

**`WUD_Default.bin` 使用游戏自身的固定密钥，不绑定 APK 签名。** 原版存档可以被重新签名的修改版直接读取，无需转换，因此"先导出存档，再换装重签名版"这条路径成立。

### <a id="save-transfer"></a>导出与恢复验收

导出前先让游戏完成落盘：在游戏内正常保存，回到主界面等待几秒，再完全强制停止并取出文件。

恢复时遵循[文件恢复的属主与权限](adb.md#restore-ownership)：先让新版本创建私有目录，再逐文件覆盖，不替换整个数据目录；属主应与新文件一致，权限通常为 `0600`。本系列中，属主错误的表现是游戏**把存档当作不存在**并直接建立新档，不报错，因此很容易被误判为存档不兼容。

卸载原签名 APK 前，必须**实际取得**主文件与 `.bac`，并记录大小和哈希；仅确认 `allowBackup=true` 不够。无 root 真机、鸿蒙 HDC 与卓易通环境的取数边界见[设备侧取数通道](adb.md)，破坏性操作的验收条件见[迁移前置检查](adb.md#migration-prerequisites)。

## <a id="store-repair"></a>停服后商城的本地发货

### <a id="store-call-chain"></a>发货调用链

支付界面仍在，但支付 SDK 或服务器已不可用。两代的商品发放**原本就在 native 的 `Java_com_catcap_Base_cpay` 中完成**：按商品 ID 更新金币、衣柜和解锁状态，再调用 `Player::saveProfile()`；Java 支付层只是成功回调之前的传输通道。

### <a id="store-patch"></a>Java 层短接

保留原界面和发货逻辑的最小改动是：

```text
爱养成2：Fiap.android_pay(productId) -> Base.pay(productId)
爱养成3：Fiap.android_pay(productId) -> Base.pay(productId, 1)
```

《爱养成3》的第二个参数 `1` 来自原版购买成功路径，不是自行编造。这个改法不动 native 库，也不改商品编号、价格文字或存档实现。

### <a id="store-validation"></a>成品验收

通用的构建、签名和成品反编译要求见[改包的构建、签名与成品验证](apk.md#build-verify)。本案例依次完成：重建；重签并验证 v2 / v3；从**最终 APK**反编译目标类，确认调用已生效；在真机中点击原商城商品，确认奖励实际发放。四项均已通过。
