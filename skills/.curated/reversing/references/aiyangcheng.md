# 爱养成系列

《爱养成》系列 Android 重打包版的完整还原记录：资产怎么解、规则表怎么读、结局判定在哪几个函数里、以及**用户问"某结局怎么达成"时该按什么格式回答**。

> 实测快照：《爱养成2》2.9.7.4（`cn.actcap.ayc2`）、《爱养成3》1.7.4（`cn.actcap.ayc3`）。结论均由反汇编、解密后的资产、成品反编译或真机操作验证。通用方法见 [APK 与 native 库的静态逆向](apk.md)。

## <a id="structure"></a>应用结构

两代主体都是 Cocos2d-x C++：

- 游戏逻辑集中在 `lib/armeabi-v7a/libcocos2dcpp.so` 与对应的 `arm64-v8a` 库，**没有 strip**，`GameManager`、`Player`、`EventLayer`、`EndLayer`、`PlaceLayer`、`PhotoAlbumLayer`、`CCSVParse`、`IapStore` 等 C++ 符号全部保留。查符号表永远是第一步。
- Java / Dex 层主要承担 Activity、JNI 桥接、广告、支付和系统能力；`com.catcap.Catcap` 是 C++ → Java 的主要桥。
- 包里同时含 AndroidX、穿山甲广告 SDK 等较新组件，而签名密钥创建于 2014/2015 年——典型的"旧游戏本体 + 新发行壳"。

## <a id="asset-decrypt"></a>资产解密

调用链直接写在符号表里：

```text
CCSVParse::openFile()
  -> rc4_base64_decrypt("dhopNVDUg97ijxDe", data)
```

解密流程就是 `plaintext = RC4(key, Base64Decode(assetBytes))`，两代共用同一个密钥。

| 作品 | CSV 数量 | 位置 |
|---|---:|---|
| 爱养成2 | 2172 | `assets/*.csv` |
| 爱养成3 | 1302 | `assets/ios_chs/csv/`、`assets/ios_cht/csv/` |
| 合计 | 3474 | |

简体文件通常带 UTF-8 BOM、繁体 `_ft` / `ios_cht` 不带，所以两组密文从第一个字节起就不同——是明文差异，不是两套密钥。批量解密要以"UTF-8 解码成功"为回退门槛，实测 3469 个走 RC4、5 个本来就是明文，可全量还原且无误判。

## <a id="data-model"></a>数据模型

CSV 分两类，混在同一个目录里，靠第一行区分：**规则表第一行通常是中文字段名，剧本文件第一行直接是指令**。

**剧本文件**是一套轻量的行驱动 VM，列为：

```text
say emote in out scene music cgin cgout word reward choose fin
```

分支写成 `rewardId||选项文本||跳转行号`；文本支持 `$kidname` 一类变量插值，`|` 表示分页或换段。两代合计约 40270 行剧本指令。

**规则表**相当于随包附带的设计文档：

- `goout.csv` / `celebration.csv` / `workbook.csv`：地点、时间、前置事件、优先级、课程 / 打工次数和属性阈值。
- `end.csv`：结局判定条件（本篇重点）。
- `reward.csv`：属性、货币、角色好感度和解锁项的增量。
- 爱养成3 另有 `monster.csv`、`wing.csv`、`piece.csv`，覆盖战斗、翅膀和服装碎片。

**男女主线用文件名后缀分流**，由 `GameManager::AddBoy()` 按存档里的性别字段把 `<name>.csv` 换成 `<name>_boy.csv`（格式串 `%s_boy.%s`）。所以男主线看 `end_boy.csv`、`goout_boy.csv`，女主线看无后缀版本，两张表互不影响。

两代属性模型不同：

```text
爱养成2：体力 智力 武力 法力 气质 魅力 体贴 道德 感受 叛逆
爱养成3：体力 疲劳 魔力 武力 智力 魅力 体贴 技能 光属性 暗属性
```

## <a id="ending-tables"></a>结局表的列语义

`end.csv` / `end_boy.csv` 的列（中文行 / 英文行两行表头）：

```text
编号 结局名称 体力 疲劳 魔力 武力 智力 魅力 体贴 技能 知名度 黑暗 金币
npc编号 好感度 修炼 次数 必要事件 必要服装 冒险次数 艾泽尔 切西亚 光暗礼包 魔精灵礼包
endID name energy tired magic force iq glamour thoughtfulness raise popular dark coins
npc love class times necessary cloth adventure azel chelsea packa packb
```

判定语义（来自 `EndLayer::checkEnd()`）：

- **空单元格 = 不检查**。判定循环先跳过空值，不计入"需满足项"计数。
- **正数 = 下界**（玩家值 ≥ 要求）；**负数 = 上界**（玩家值 ≤ 绝对值）。汇编里是取符号位分支，负数支先取绝对值再比 `le`。
- `npc` + `love` 成对：指定角色的好感度 ≥ `love`。
- `class` + `times` 成对：指定课程 / 打工安排次数 ≥ `times`。
- `necessary`：玩家已触发事件列表里**必须包含**该事件 ID（`containsString` 判定）。
- `azel` / `chelsea` / `packa` / `packb`：需解锁对应角色剧情或购买对应礼包。
- **逐行扫描，"满足数 == 需检查数"即命中，表中靠前的行先胜出**——这是截胡的根源。

## <a id="panel-rendering"></a>结局面板的渲染与硬编码黑名单

图鉴里点大图弹出的条件说明由 `PhotoAlbumLayer::onBigPhoto()` 生成。它做两件事，都是理解"为什么条件对不上"的关键。

**第一件：开头就查一张写死的 ID 黑名单。**

```text
arrayWithObjects("760","730","705","715","716","744","745","746", NULL)
if (containsString(list, endID)) → 显示 RBS[6] = "特殊结局~ "，直接返回
else                            → 逐字段拼条件文案
```

这八个 ID 是**四对对称的男女结局**（女 705/715/716/730 ↔ 男 744/745/746/760）。可观察的事实是：这批条目的条件展示被代码显式跳过，而它们恰好构成隐藏要素的全集；至于作者出于什么意图这样圈定，属于推测，不写进结论。实用价值在于**这张表本身就是一份隐藏要素清单**。

**第二件：非黑名单条目逐字段拼文案，但只覆盖部分字段。**

| 字段 | 渲染成 | 备注 |
|---|---|---|
| `AttributeName.plist` 里的键 | `体力>600` / `体贴<300` | 含 energy tired magic force iq glamour thoughtfulness raise popular dark **coins**；正数用 `>`、负数用 `<` 加绝对值 |
| `npc` + `love` | `苏瑞尔的友好度大于4心` | 心数 = `ceil(love × 0.5)`，即好感 8 显示成 4 心 |
| `class` + `times` | `安排魔法次数大于30次` | 课程名查 `classname.plist` |
| `azel` / `packa` / `packb` | `需要解锁艾泽尔剧情` / `需要购买光暗礼包` / `需要购买魔精灵礼包` | 固定文案 |
| `necessary`、`cloth`、`adventure`、`chelsea` | **没有渲染分支** | 对**所有**结局都不显示 |

**面板的 `>` / `<` 实际是 `≥` / `≤`。** 判定用的是 `cinc ..., ge` / `cinc ..., le`，界面措辞差了一档。边缘数值以判定函数为准。

所以隐藏是双重的：黑名单里的条目**整条**看不见；不在黑名单里的条目，`必要事件` 这类字段也照样看不见。

## <a id="event-branch"></a>native 里的事件分支

有些 `necessary` 引用的事件 ID 在任何 CSV 里都找不到定义——它们由代码生成。爱养成3 里 `PlaceLayer::onEventFin()` 有一张 `switch`，某个事件播完后调：

```text
addChooseEvent(<触发事件ID>, <选项A事件ID>, <选项B事件ID>)
```

按钮贴图是 `map/choose_<触发事件ID>_a.png` / `_b.png`（男主线加 `_boy` 后缀），把图看一眼就知道两个选项的文案。**A 绑定第二个参数、B 绑定第三个参数**（反汇编里 `w2` 先装进 A 的回调 tag、`w3` 装进 B 的）。

这类二选一**不可回头，且互斥**：同一次选择产生的两个事件 ID 永远不可能同时出现在存档的已触发列表里。凡是两条结局分别要求这两个 ID，它们就结构互斥，不必再算数值。

## <a id="report-format"></a>结局达成条件的汇报格式

**用户问"某结局怎么达成 / 需要什么条件"时，按下面三节回答，不要只报目标行的数值。** 只给数值会漏掉两类致命信息：面板不显示的隐藏门槛，以及被前面的行截胡。

### <a id="report-target"></a>目标结局

一张纵表，六行固定：

| 项 | 内容 |
|---|---|
| **面板描述（游戏内）** | 玩家实际看到的原文。黑名单条目就写 `特殊结局~ ` |
| **面板本该显示的文案** | 用还原器按渲染规则重新生成一遍，让用户看到被藏了什么 |
| **真实要求** | 判定函数的完整条件，用 ≥ / ≤ 写清方向，附上面板不显示的字段 |
| **无要求项** | 显式列出"不检查"的属性——这是后面找规避杠杆的依据 |
| **前置事件怎么拿** | 事件链 + 分支选项原文 + 不可回头的提醒 |
| **代码依据** | 面板黑名单 / 判定 / 事件分支各自落在哪个函数 |

### <a id="report-preempt"></a>可能截胡的结局

**把目标行之前的每一行都列出来**，一行都不省——用户需要看到"我已经替你排除了这些"。列固定为：

| 编号 | 名字 | 面板描述（游戏内原文） | 面板没说的门槛 | 对目标的威胁 |
|---|---|---|---|---|

威胁一栏给判断和客观理由，用固定词汇：

- `永不可能`——数值区间互斥，写明哪个属性的上下界打架。
- `结构互斥`——两行分别要求同一次二选一产生的互斥事件。
- `高危` / `中危`——数值上能同时成立。分级依据要写成客观事实（比如"数值门槛被目标行完全包含，只差某两项"比"最高危"更有信息量），别只给一个主观标签。
- `门槛够不着`——某属性要求远高于该周目的合理范围。这依赖对玩家养成路线的假设，属于推断，要标明前提。

### <a id="report-safezone"></a>威胁结局的完整条件与安全区

对判定为高危 / 中危的几条，各给一份**完整条件清单**（和目标结局同规格，用户要能直接照着规避），然后给具体的规避区间：

- 优先找"目标行完全不检查、而威胁行强制要求"的属性，把它卡在威胁行够不到的区间——不影响目标行，是免费的隔离带。
- 给出至少一个备选方案及其代价，让用户能反驳。

### 汇报纪律

- 每条结论标注来源函数或表行；实测与推断分开标（比如时间列的 `年|月|日` 解读是从表内模式推的，就直说没有代码直接佐证）。
- 面板文案必须是**还原器生成**的，不是手抄 CSV——还原器能同时验证你对渲染规则的理解是否正确。
- 截胡分析要机械化算（逐属性求上下界交集），不能凭印象说"这个应该不会冲突"。

## <a id="save-file"></a>存档文件

游戏自写的 `WhyUserDefault` 默认文件名：

```text
WUD_Default.bin
WUD_Default.bin.bac
```

`WUD_Default.bin` 含 `playerInfo`、金币、衣柜、事件、结局和照片 ID 等数据；`.bac` 是写入时生成的滚动备份。Cocos2d-x 的 `UserDefault.xml` 只承担附加偏好，不能替代主存档。Android 内部路径通常为：

```text
/data/user/0/<android-package>/files/WUD_Default.bin
```

卸载原签名 APK 前必须**实际取得**主文件和 `.bac`、记录大小与哈希；仅确认 `allowBackup=true` 不够。鸿蒙 / 卓易通环境下的取数边界见 [鸿蒙与 ANCO 容器](harmonyos.md)。

## <a id="store-repair"></a>停服后商城的本地发货

支付 UI 仍在但支付 SDK / 服务器已不可用。两代的商品发放**本来就在 native 的 `Java_com_catcap_Base_cpay` 里完成**：按商品 ID 更新金币、衣柜和解锁状态，再调 `Player::saveProfile()`；Java 支付层只是成功回调之前的传输通道。

保留原 UI 和发货逻辑的最小改动：

```text
爱养成2：Fiap.android_pay(productId) -> Base.pay(productId)
爱养成3：Fiap.android_pay(productId) -> Base.pay(productId, 1)
```

爱养成3 的第二个参数 `1` 来自原版购买成功路径，不是自己编的。这个改法不动 native 库、不改商品编号 / 价格文字 / 存档实现。

验收四步（构建、签名、成品反编译的通用要求见 [改包的构建、签名与成品验证](apk.md#build-verify)）：重建 → 重签并验证 v2/v3 → **从最终 APK 反编译目标类**确认调用已生效 → 真机点原商城商品确认奖励实际发放。本案例四步均已完成。
